## 1. 三条不可协商的原则

| # | 原则 | 为什么 |
|---|---|---|
| 1 | **有意义的输出必须落文件** | 终端输出**随会话消失**。M6 侦察时实测：35 处裸 `console.*` 分布在 6 个文件里，其中 `dev-workflow.ts` 19 处——包括「红线拦下了这次工具调用」「闸门判负」这类**事后必须能举证**的事实。会话一关，这些事实从世界上消失 |
| 2 | **每条事件必须能归到某个 run** | 多 run 会交错写进同一个文件。不能按 run 分组时，「这个错误属于哪一次运行」无法回答——M6 之前真实覆盖率 **0/701** |
| 3 | **观测失败不得阻断业务**（fail-open） | 日志写不进去（权限 / 磁盘满 / 路径是目录）时**吞掉 + stderr 告警**，run 必须照常跑完。这与质量闸门的 fail-closed **刻意相反**：闸门拦的是「不该放过的产物」，日志只是辅助能力 |

### 原则 2 的历史事故（必须知道，否则会重犯）

M6 之前的签名是 `stageStart(stageName: string, runId?: string)` —— **两个形参都是 `string`**。
于是有人写了：

```ts
stageStart('merge', 'rejected');   // 语义串进了 runId 槽，编译器一声不吭
stageStart('merge', 'resumed');
```

结果：701 条事件里带 `runId` 的只有 6 条，而这 6 条的**值全是 `"rejected"` / `"resumed"`**
——真实 runId 一条都没有，日志实际退化成「一个混装所有 run 的大文件」。

**修法不是加注释，是让误用无法通过编译**：现在参数是对象（`{ stage, runId }`）且两者都必填。
运行期还留了一道负向断言（见 §5.3）。

## 2. 输出通道（谁写哪儿）

| 通道 | 文件 | 用途 | 可否新增裸写入 |
|---|---|---|---|
| **结构化事件**（唯一真相源） | `logs/dev-workflow.log`（JSON Lines，可轮转） | 所有运行期事实 | ✅ 走 `progress.ts` 的写 API |
| 终端镜像 | stdout / stderr | 人实时看（`tail -f`） | ❌ 由 logger 统一产出，**不允许**业务代码自己打 |
| 应用日志 | `logs/my-midway-project/*.log` | Midway 框架自身的请求日志 | ⚠️ 目前**基本空转**（`common-error.log` / `midway-core.log` 全 0 字节）。本规范**不依赖**它，也不要求业务代码写它 |
| 验证脚本证据 | `logs/m*-verify.log` | 验收证据，**追加写** | ⚠️ 目的不同（证据 vs 运行日志），不适用本规范；但**禁止覆写**（本项目覆写丢过证据） |

> 📌 **为什么不把 `@midwayjs/logger` 当作统一出口**：它是**应用级** logger（面向 Web 请求维度），
> 而本项目要追踪的是 **run 级** trace。维度不匹配，硬套会让 `runId` 无处安放。
> 📌 **为什么不用 Mastra 的 `Logger`**：M1 卡里写着「已用于每步打点」，实测 **`src/` 里零 import**
> ——那是建卡时的预期被写成了事实。M6 选择继续演进 `progress.ts`（零迁移成本、701 行历史格式兼容）。

## 3. 事件名闭集

定义在 `progress.ts` 的 `ProgressEvent` 联合类型。**新增事件名必须先改类型**（编译期强制）。

| 事件 | 语义 | 关键字段 |
|---|---|---|
| `run:start` | 一个 run 开始（由 workflow 的**第一个 step** 落） | `workflow` / `issueNumber` |
| `run:suspend` | run 挂起等人（**不是** `step:start`） | `waitingFor` |
| `run:end` | run 终态（每个 run **有且仅有 1 条**） | `status` / `durationMs` / `failedStage` / `stepsDone` / `stepsFailed` / `llmCalls` |
| `step:start` / `step:done` / `step:fail` | 阶段边界 | `durationMs`（done/fail 有） |
| `llm:start` / `llm:done` / `llm:retry` | 一次 LLM 调用 | `attempt` / `durationMs` / `usage` |
| `guard:deny` | 权限围栏拦下一次工具调用 | `tool` / `reason`（**不得记入参**，可能含凭据） |
| `test:run` / `test:touch` | 程序侧测试事实 / 自证检测 | `command` / `exitCode` / `testsPassed` / `modified` |
| `repo:target` / `repo:lock` / `repo:unlock` | 多仓库目标与互斥锁 | `repoKey` / `localPath` / `waitedMs` |
| `config:check` | 配置体检（启动期） | `level` / `field` / `summary` |
| `inbound:error` | 入口轮询的错误（进程级） | `kind` / `messageId` |
| `log:rotate` / `log:write-failed` / `log:invalid-runid` / `trace:missing` | **日志模块自身**产出（`stage: 'logger'`） | 见各自字段 |

> `llm:retry` 的准确语义是「**本次尝试失败**」（含重试预算耗尽的那一次）。
> 是否还会再来一次，看 `attempt` 与 `maxAttempts`，不要靠事件名的字面意思推断。

> 📌 **「一张卡片发出去没有」查哪里？** 查 `stage: 'notify'` 的 `step:done` / `step:fail`：
> 成功记在 `step:done`（`mode` 字段），失败记在 `step:fail`（`mode` / `feishuError` / `raw`）。
> **本轮曾声明过一个 `notify:send` 事件名，收口时自查删除** —— 它没有任何生产者，
> 留着会让人以为「查 `notify:send` 就能看到推送结果」。
> 这与本卡 §2 点名要修的 `Logger` 幻觉（`M1-只读洞察闭环.md:90` 写了却从未 import）**是同一类错**：
> **闭集里不允许存在没有生产者的名字。**

### 3.1 `step:start` 的准确语义（**不是「该步 execute 被调用」**）

`step:start` / `step:done` 的语义是 **「该步进入了实质性工作」**，**不是**「该步的 `execute` 函数被执行了」。
两者在 `stopAfterCommit` 路径上**确实会分离**：

| 事实（2026-09-17 实测，runId `7821d833`） | 说明 |
|---|---|
| 日志里有 `repo:unlock`，其 `stage: 'push-open-pr'` | 放锁写在 push-open-pr 步的 `finally` —— **该步确实执行了** |
| **但没有** `push-open-pr step:start` / `step:done` | `runPushOpenPr()` 在 `stopAfterCommit` 时**未到 `stageStart` 就提前 return**（零远端，没干活） |

所以三条推论，查日志时必须遵守：

1. **`field: stage` 是「归属标签」，不是「执行凭证」** —— 它回答「这条事件属于哪一步的责任范围」，
   不回答「这一步跑过没有」。`repo:target` / `repo:lock` / `repo:unlock` 的 `stage` 都属此类。
2. **判断「某阶段是否执行过」只能看 `step:start`**（见 §9 的查询手法）；
   ⚠️ 反过来说，**「某阶段没执行」不能用「没有 `step:start`」去反推业务是否完整** ——
   `stopAfterCommit` / 未配置 GitHub 两条路径都会让 push-open-pr 空转，
   这是设计（见 `dev-workflow.ts:1093`），不是缺事件。
3. 因此 §10 的配对校验只看 `(runId, stage)` 的 start↔done/fail 数量，
   **不会**（也不该）把「有 `repo:unlock` 无 `step:start`」判成不平衡 —— 它本来就不是 step 事件。

> 📌 **为什么值得写下来**：直觉上「有事件 = 跑过了」，而这里恰好是反例。
> 若后人拿 `step:start` 当执行凭证去算「八步完成率」，`stopAfterCommit` 的 run 会被误判成
> 「少跑了一步」，进而去修一个并不存在的 bug。

## 4. 阶段名闭集

定义在 `progress.ts` 的 `STAGE_NAMES`。**阶段名进 `traceId`**（`` `${runId}:${stage}` ``），
也是「按阶段算耗时 / 算 token」的分组键 —— 拼写漂移会把同一阶段拆成多行，
而**汇总数字看起来仍然正常**（静默的统计错误）。故用联合类型钉死。

```
启动/进程级： startup · logger · inbound
dev-workflow： checkout · coding · test · review · commit · push-open-pr · notify · merge
闸门机制：     gate        （质量闸门内部的 LLM 调用，不属于八步中的任何一步）
insight：      collect · summarize · confirm
```

新增阶段 = 改 `STAGE_NAMES` + 更新本节 + 更新 `milestones/README.md` 里的步骤表（如果有）。

## 5. 字段规范

### 5.1 必填（两个，缺一编译不过）

| 字段 | 类型 | 说明 |
|---|---|---|
| `stage` | `StageName` | 见 §4 |
| `runId` | `string \| null` | **取不到时必须显式写 `null`**，不允许省略 |

⚠️ **为什么是 `null` 而不是省略**：`JSON.stringify` 会**丢掉** `undefined` 字段，
于是「忘了传」与「显式声明不属于任何 run」在文件里长得一模一样，无法区分。

### 5.2 自动生成（调用方不写）

| 字段 | 生成规则 |
|---|---|
| `ts` | ISO 8601，写入时刻 |
| `traceId` | `` runId ? `${runId}:${stage}` : null `` —— 按 OTEL span 语义命名，便于将来换 sink 而非换模型 |
| `event` | 见 §3 |

> 📌 `traceId` 字段**同时是格式标记**：只有 M6 之后写出的记录才带它。
> 因此「哪些记录受本规范约束」不需要靠时间戳猜 —— 有 `traceId` 即为新格式。

### 5.3 `runId` 的三个约束

1. **不得取语义串**。运行期拒绝 `STAGE_NAMES` 全集 + `rejected` / `resumed` / `approved` /
   `true` / `false` / `undefined` / `null` 这些值 —— 命中时该字段按 `null` 处理，
   原始值记进 `invalidRunId`，并额外落一条 `log:invalid-runid`。
2. **首尾空白被规整**；空串视为 `null`。
3. **归不到 run 时不静默**：`stage ∉ {startup, logger, inbound}` 且 `runId === null` 时，
   额外落一条 `trace:missing`（带 `originalEvent`）—— 让遗漏变成**可数事实**。

### 5.4 金额与用量

`usage` 归一成 `{ inputTokens, outputTokens, totalTokens }`，**兼容** AI SDK v5（`input/outputTokens`）
与 v4（`prompt/completionTokens`）两套命名。

> ⚠️ **拿不到就是 `null`，绝不等价于 0。**
> 「中继没返回 usage」与「这一轮真的花了 0 token」是两件完全不同的事。
> 把后者写成 0 会让成本报表变假，且**不会让任何东西报错** ——
> 与 M4 的 `testsPassed = null ≠ true` 同构。

## 6. 级别与镜像

**没有「日志级别」这个概念**，只有「这条事件是否属于失败/异常」。镜像规则（`isWarn`）：

| 走 stderr（`console.warn`） | 走 stdout（`console.log`） |
|---|---|
| `*:fail` / `*:retry` / `guard:deny` | 其余 |
| `run:end` 且 `status ∉ {ok, skipped}` | `run:end` 且 `status ∈ {ok, skipped}` |
| `notify:send` 且 `ok === false` | — |
| `log:*` / `trace:missing` | — |
| `inbound:error` / `config:check` 且 `level !== 'info'` | — |

镜像行格式（**不是**解析对象，只为人眼服务）：

```
[<ISO ts>] <stage> <event>[ (<n>s)] run=<runId 前 8 位> [| k=v ...]
```

## 7. 禁止事项

### 7.1 禁止裸 `console.*`（白名单：`progress.ts` 自身的 4 处）

```bash
grep -rn "console\." src/ --include=*.ts
```

期望结果**只有** `progress.ts` 里的 4 处：

| 位置 | 是什么 | 为什么必须留着 |
|---|---|---|
| `progress.ts` 镜像 2 处 | `console.log` / `console.warn`（终端镜像本体） | 它就是镜像机制本身 |
| `progress.ts` 写失败告警 1 处 | 「写日志失败(不影响流程)」 | **落盘已失败**，只能走 stderr（写文件去报告写文件失败是死循环） |
| `progress.ts` 轮转提示 1 处 | 轮转发生提示 | 同上，轮转是存储层动作、无 run 可归属 |

⚠️ **一处也不能多**。业务代码里出现 `console.warn` 意味着：这条信息**只活在终端里**。
需要留痕就先想清楚它属于哪个阶段、哪个 run，再用 `stage()` / `stageStart()`。

### 7.2 其他禁止

- ❌ 手工构造 JSON 行写进 `logs/dev-workflow.log` —— 必须走写 API（否则 `traceId` / `runId` 规整会绕过）
- ❌ 把本机 clone 路径写进**快照**（`ContextSchema` / `mastra.db`）。日志里**可以**写
  （`repo:target.localPath` 是「串台」唯一的判据），但那是**唯一**例外，且两者性质不同
  （日志 = 事后证据；快照 = 跨机器状态）
- ❌ 把工具调用入参写进日志（可能含 `.env` / token）—— 只记工具名与原因摘要
- ❌ 覆写任何 `logs/*.log`（追加写；覆写丢过证据）
- ❌ 用拼接标识（`:` / `_`）当文件名 —— `:` 是 Windows 文件名保留字符，见
  `milestones/M7-飞书双向控制.md` §11 2026-09-17

## 8. 轮转与保留

| 环境变量 | 缺省 | 含义 |
|---|---|---|
| `PR_AGENT_PROGRESS_FILE` | `<cwd>/logs/dev-workflow.log` | 日志文件绝对路径 |
| `PR_AGENT_PROGRESS_LOG` | 未设（= 开启） | 设 `0` 完全关闭落盘**与镜像**（不留半开状态） |
| `PR_AGENT_LOG_MAX_BYTES` | `5242880`（5 MiB） | 单文件超过即轮转；`0` = 永不轮转 |
| `PR_AGENT_LOG_KEEP` | `5` | 保留的轮转份数（不含当前文件） |

轮转命名：`dev-workflow.log` → `.1` → `.2` …（**编号越大越旧**）。

### 读取契约（`log-store.readAllRecords`）

**先读最旧的轮转文件，最后读当前文件**（`base.keep` … `base.1`, `base`），
拼出来天然是时间顺序 —— **不按 `ts` 排序**，因为同一毫秒的多条事件会被重排。

⚠️ 有界保留意味着：**一个 run 的事件只有在「不超过 `keep` 份文件」的前提下才保证完整**。
调小 `keep` 或写超长事件前，先看 `test/mastra/log-store.test.ts` 里那条
「超出 keep 的最旧轮转文件会被丢弃」的用例。

## 9. 怎么查（把手工手法消掉）

M6 之前要查「某个 run 走到哪了」，必须：先去 `mastra.db` 的 `mastra_workflow_snapshot`
反查 runId → 再在混杂日志里按 `checkout step:start` 手工切分。**M6 消掉了这个手法。**

```bash
# 1) 重建一个 run 的八步时间线 + token 汇总 + 配对校验（不读 mastra.db）
node scripts/verify-m6-observability.js --report <runId>

# 2) 全库排查
node scripts/verify-m6-observability.js --pairing      # start↔end 配对（含历史偏差报告）
node scripts/verify-m6-observability.js --cost         # 按仓库聚合 token
node scripts/verify-m6-observability.js --console      # AC-2：裸 console 白名单校验

# 3) 程序里
import { readRun, pairingReport, costByRepo } from '../mastra/log-store';
```

历史遗留说明：M6 之前的 701 条事件**没有 `runId`**。它们会被归到
「`runId: undefined`」桶里 —— **不丢弃、不报错、也不参与配对断言**（见 §10）。

## 10. 配对校验（AC-4）

`pairingReport()` 按 `(runId, stage)` 统计 `step:start` 与 `step:done + step:fail`。

| 桶 | 含义 | 是否作为判据 |
|---|---|---|
| `unbalanced`（`runId` 非空） | M6 之后的数据不平衡 | ✅ **是**，非空即失败 |
| `legacyUnbalanced`（`runId` 为 null/缺失） | M6 之前的数据 | ❌ **只报告**，不参与断言 |

⚠️ **抹平历史偏差 = 伪造历史。** M6 侦察时量到的三处不对称
（`step:start` 141 vs `step:done+fail` 146 = 多 5 个 end；`repo:lock` 9 vs `repo:unlock` 6；
`llm:start` 182 vs 终态 173）必须**报告出来**，且要能解释成因。

> 📌 那「多 5 个 end」的成因已在 M6 查明并修复：闸门判负处先 `p.fail(msg, {...})` 再
> `throw`，异常冒泡到本步 catch 又一次 `p.fail(e)` —— **一个 step 落两条 `step:fail`**。
> 修法是引入 `StepFailError`（判负处只 throw，`p.fail` 由 `terminateStep` 唯一负责）。

## 11. 与 OTEL 的关系（M6 明确不做 OTEL，但保留迁移路径）

**不做**：本项目当前没有观测后端，写本地文件的收益（零依赖、可直接 `tail`）更直接；
且 M6 的判据是**可关联**，不是**可上报**。

**保留迁移**：字段已按 span 语义命名（`ts` = span start、`durationMs` = span duration、
`traceId` = `runId:stage`）。将来真出现多实例 / 多机分布式追踪需求时，
**换的是 sink，不是数据模型** —— 把 `appendRecord` 换成 OTEL exporter 即可，
所有调用点不动。
