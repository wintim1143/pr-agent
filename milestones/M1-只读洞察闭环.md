## 1. 目标（一句话）

**飞书（或 HTTP）发起一句自然语言请求 → 通过 Mastra 的 GitHub 集成只读拉取当前项目的 issue 与提交记录 →
交给 Mastra Agent 汇总成洞察 → 推一张飞书卡片回群里 → 卡片按钮触发 workflow resume 完成闭环。
全程对目标仓库零写入。**

---

## 2. 为什么现在做（排序理由）

| 理由 | 说明 |
|---|---|
| **绕开 D4 未决项** | 目标仓库选「自举」还是「demo 仓库」一直没定。M1 **只读**，不建分支、不改文件、不开 PR，D4 直接不再是阻塞项。 |

| **提前验证飞书主入口** | 原规划把飞书放在 S5（后置）。但这是 IM 驱动项目，入口就是产品本身，后置等于项目长期没有入口。 |

## 3. 范围 / 明确不做

**做**

- GitHub **只读**：列 issue、取单个 issue、列提交记录
- 飞书：**发**卡片、**收**消息（先轮询，后升级长连接）
- Mastra：Integration 抽象、Tool、Workflow（含 suspend/resume）、Agent 结构化输出、Storage 跨请求恢复
- 触发：HTTP 端点 + 飞书群消息

**明确不做**（留给 M2 及以后）

- 不调用编码 agent，不产出任何代码改动 —— 用户明确要求
- 不 `git checkout` / `git commit` / `git push` / 开 PR / merge
- 不做需求解析后的 issue 创建
- 不做测试闸门 / 审核闸门（那是 M4）
- 不做多仓库、不做 GitHub App 鉴权（M5）

## 4. 链路图

```
触发层                编排层                     集成层                  外部
──────                ──────                    ─────                  ────
POST /api/insights ─┐
                    ├─→ insight-workflow ──┬─→ step1 collect ──→ githubIntegration ──→ api.github.com
飞书群消息 @bot ─────┘                      │     (只读 tools)        (Integration)        GET /repos/.../issues
                                           │                                              GET /repos/.../commits
                                           │
                                           ├─→ step2 summarize ─→ insight-agent (LLM)
                                           │     (structuredOutput)
                                           │
                                           ├─→ step3 notify ────→ feishuIntegration ──→ 飞书群卡片
                                           │                                             [✅ 确认 / 🔄 重跑]
                                           │
                                           └─→ step4 confirm ──── suspend() 挂起
                                                    ↑                    │
                                                    │                    ↓
                                      卡片按钮回调 ──┴──→ POST /api/workflows/insight-workflow/resume?runId=xxx
                                                          (Storage 恢复上下文 → 走到终态)
```

关键点：**step4 的 resume 是一个全新的 HTTP 请求**，手里只有 `runId`，
必须靠 LibSQLStore 把 step1–step3 的上下文捞回来。这条链路在 `src/mastra/index.ts:29-40` 有实测记录：
不配 storage 时 resume 必报 `This workflow run was not suspended`。所以 M1 同时也是对 Storage 的验收。

> 📊 **数据流向图（时序图）**：[`M1-只读洞察闭环-flow.md`](./M1-只读洞察闭环-flow.md) —— 用 Mermaid 画出「飞书消息 → 触发 workflow → collect → summarize → 卡片回推 → suspend → 人工 resume」的完整数据流向与跨请求断点。

## 5. 用到的 Mastra 模块（本里程碑重点）

| Mastra 模块 | 导入路径 | 在 M1 中的职责 | 为什么用它，而不是裸写 |
|---|---|---|---|
| **`Integration`** | `@mastra/core/integration` | GitHub / 飞书两个外部系统的官方集成基类。继承后覆写 `listStaticTools()` 与 `getApiClient()` | 它把「认证 + 工具集 + API client」收敛成一个对象，agent 和 workflow 拿到的都是同一套；裸写 fetch 只能给 workflow 用，agent 用不了 |
| **`createTool`** | `@mastra/core/tools` | 把 GitHub 只读能力声明为带 zod 输入输出 schema 的 tool | zod schema 自动生成参数校验与 JSON Schema，Studio 里能直接看到和手测；裸函数没有这些 |
| **`Workflow` + `createStep`** | `@mastra/core/workflows` | 四步编排，`suspend()` / `resume()` 人工关卡 | 强制顺序执行 + 状态落盘，是「闸门不可跳过」的载体 |
| **`Agent` + `structuredOutput`** | `@mastra/core/agent` | 汇总洞察，输出固定 schema 的 JSON | `structuredOutput` 直接给结构化对象（`result.object`），不用解析 LLM 自由文本 |
| **`LibSQLStore`** | `@mastra/libsql` | 已配（`src/mastra/index.ts:42`）。M1 验收它的 suspend/resume 恢复能力 | 见上文，人工确认链路在设计上依赖它 |
| **`MastraServer`** | `@mastra/koa` | 已挂载（`src/mastra/server.ts`），提供 `/api/workflows/*/start-async`、`resume`、`runs` 等端点 | 已实测存在，不需要自己写 HTTP 入口（这是上一轮的纠正） |
| `Logger` | `@mastra/core/logger` | 每步打点，便于排障与后续成本统计 | — |

### 5.1 关于「收发飞书」的模块选型（重要）

核对过 `@mastra/core/channels`（Mastra 1.63 的 Chat Channel 抽象）后，**M1 不套它**，原因：

- 它本质是 **agent 流式输出的渲染适配层**（`ChatChannelProcessor` 只是往 system prompt 里注入频道上下文的 input processor，
  见 `node_modules/@mastra/core/dist/channels/processor.d.ts:7-16`），附带一个 Slack compat。
- 我们要的是 **workflow 级的卡片通知 + 按钮回调**，不是把 agent 的 token 流渲染成聊天消息。两者不是一回事。
- 官方只有 Slack 实现，飞书要照着 compat 层写一套，属于未文档化探索，不该放在「最短路径」里。

**M1 采用**：自己实现 `feishuIntegration`（继承 `Integration` 基类），收/发各自封装成 tool 或 service：

| 方向 | 方案 | 依据 |
|---|---|---|
| **发** | 复用现有 `src/mastra/adapters/feishu.ts`（webhook / 自建应用两模式） | 已实现且已验证 |
| **收（M1-3a，最短路径）** | 轮询拉取会话历史消息：`GET /open-apis/im/v1/messages?container_id_type=chat&container_id={chat_id}&start_time={ts}&sort_type=ByCreateTimeAsc`，走 `tenant_access_token` | 官方文档确认该接口存在且支持应用身份。**零新依赖、无需公网 IP**，本机可跑 |
| **收（M1-3b，升级）** | 装 `@larksuiteoapi/node-sdk`（1.73.2）走 WebSocket 长连接，事件实时推送 | 同样无需公网 IP，且是正解。轮询只是先跑通 |

**收消息的前置条件**（飞书侧，需人工确认）：

1. 应用已启用**机器人能力**，且机器人**已加入目标群**
2. 已开通 `im:message.group_msg` 权限（群聊必需）+ `im:message` 或 `im:message:readonly` 之一
3. `.env` 里 `FEISHU_RECEIVE_ID` 是群的 `chat_id`（可用现有脚本 `scripts/feishu-list-chats.js` 拿到）
4. 群不能开启「保密模式」（开启后 `231203` 报错，拉不到消息）

若以上任一不满足，M1 **降级**：HTTP 触发 + 飞书只发不收，不影响其余环节验收。
