# M2 人工验收手册

> **给验收人**：本文档每一步都包含 ① 在哪个目录 ② 敲什么命令（原样复制即可）③ 预期看到什么输出（截取自 2026-09-07 真实运行）④ 怎么判对错。
> 全程约 10 分钟（其中端到端复跑需等待 5~15 分钟）。**复跑期间不要让电脑休眠**（实测休眠会冻结验证进程）。

---

## 0. 背景一句话：你要验收的是什么

### 0.1 M2 的主要功能

一句话：**让「自动开发 agent」第一次真正动手改代码** —— 给它一个 git 仓库和一个任务（issue），它自己建 feature 分支、改文件、跑质量闸门、提交 commit，全程只动本地、不碰远端。

对比 M1 就清楚了：

| | M1（已完成） | M2（本次验收） |
|---|---|---|
| workflow 八步编排 | ✅ 能跑通 | ✅ 不变 |
| 编码步（coding） | **占位探针**（假 agent，只返回字符串） | **真 Claude Code CLI**：真读仓库、真改文件 |
| checkout | 模拟降级 | **真建 feature 分支**（如 `feat/1-add-install-section`） |
| 三个质量闸门（test/review/commit message） | 走通即可 | **真调 LLM 输出结构化判定**（通过/打回） |
| commit | 不存在 | **真 commit 落在 feature 分支** |
| push / PR / merge | ❌ 不做 | ❌ **仍然不做**（这是 M3 的功能） |

所以 M2 验收的核心问题就三个：**改得对不对**（改动落在正确分支、内容符合任务）、**停得住吗**（不 push、main 不动、pr-agent 自己不被污染）、**失控拦得住吗**（红线文件改不了、超限显式失败）。

### 0.2 「是自己改自己吗」—— 不是

**pr-agent 是开发工具，沙箱仓库是「被开发的项目」**，两者是甲乙方关系：

- agent 干活的地点由 `CODING_REPO_ROOT` 环境变量指定，本次验证脚本硬编码指向 `D:\code\pr-agent-sandbox` —— 一个专门为验收准备的**隔离靶场**（只有 README.md / .gitignore / agent.md 三个文件，无远端）。
- agent 的所有写入都被 guard 限定在这个靶场内：写靶场外的路径直接 deny。验收 AC-10 专门验证 **pr-agent 自己分毫未动**（工作树干净、无新增分支）—— 这正是「不是自己改自己」的实证。
- 为什么先拿沙箱练：真实写入 = 破坏性操作。先在一次性靶场证明「改得对、停得住、拦得住」，之后（M3+）把 `CODING_REPO_ROOT` 指向任何真实用户仓库，行为不变。

> 顺带一提：pr-agent **开发自身**时（也就是你看的这个仓库），走的是普通开发流程，不经过 auto-dev workflow。auto-dev workflow 是**产品能力**，服务的是「未来用户提 issue → agent 自动开发用户仓库」这条主线。

### 0.3 涉及两个仓库，验收时别搞混

| 路径 | 是什么 | 验收时动它吗 |
|---|---|---|
| `D:\code\pr-agent` | 流水线本体（pr-agent 项目） | 只读（git log / 跑脚本） |
| `D:\code\pr-agent-sandbox` | 沙箱靶场（agent 干活的地方） | 只读（git 命令查看） |

## 第 3 步：亲自跑一遍端到端闭环（核心步骤，5~15 分钟）

**目录**：仍在 `D:\code\pr-agent`

**命令**：
```bash
node scripts/verify-local-write.js --reset
```

**你会看到**：脚本先重置沙箱靶场 → 打印前置检查 → 然后停在 `→ start() 中...` **静默等待 5~15 分钟**（agent 在真实调用 LLM 编码，外部后端慢属正常）。结束后打印判定。

**预期结尾**（判定汇总段）：
```
[5/5] AC 判定
  ✅ AC-1 checkout 真建 feature 分支 —— 当前分支 = feat/1-add-install-section(期望 feat/1-add-install-section)
  ✅ AC-2 coding 真改文件 —— 改动 1 个文件: README.md
  ✅ AC-3 codingResult 非占位符 —— 真实编码输出
  ✅ AC-7 三闸门输出结构化(zod 可解析) —— test.passed=... | review.decision=... | commit.message=...
  ✅ AC-8 commit 真落 feature 分支 —— HEAD=...
  ✅ AC-9 零远端(main 未动、无 remote) —— main 未变=true; 无 remote=true
  ✅ AC-10 pr-agent 工作树未被触碰 —— 分支 main→main; 工作区快照一致

=== 判定汇总: 7/7 通过 (耗时 ...s) ===
✅ 本次运行 AC 全通过
```

✅ **判对**：`7/7 通过` + `✅ 本次运行 AC 全通过`。
❌ **判错**：任何 `❌` 行，或 `GUARD_TIMEOUT`（见文末「异常怎么办」）。

> 说明：AC-7 里的 commit message **每次运行都不一样**（LLM 现场生成），内容质量差是已知遗留（闸门拿不到 diff，已记 M3 改进），**不影响验收**——AC-7/8 验的是「结构化输出能解析 + commit 真的落盘」。

```bash

```

**预期**（关键行）：

**含义**：把 agent 的干活轮数硬限到 1 轮，它没完成任务 → 系统**显式报错终止**，而不是静默截断或假装成功（workflow status=failed，无假 commit）。这正是「失控时结果可判别」的验收点。

## 异常怎么办

| 现象 | 原因 | 处理 |
|---|---|---|
| `GUARD_TIMEOUT@coding: 超过 600000ms` | 编码后端（cc-switch 代理 → 上游 LLM）慢或挂 | 等 10~30 分钟重跑；或用大预算：`VERIFY_TOTAL_GUARD_MS=2400000 CODING_TIMEOUT_MS=1800000 node scripts/verify-local-write.js --reset` |
| 闸门连续 `服务器错误`(502) | lanfengai 中继抖动 | 隔一会儿重跑（当日实测抖动频繁但会自行恢复） |
| 脚本卡住很久没动静 | ① 正常（LLM 编码慢）② 电脑休眠了 | ① 等待 ② 别合盖；休眠会冻结 Node 定时器（实测守卫迟到 63 分钟） |
| 沙箱工作区不干净报错退出 | 上次运行残留 | 加 `--reset` 重跑即可（本文档命令均已带） |
| 想先确认后端通不通 | — | 探测命令：`curl -s -o /dev/null -w "%{http_code}\n" -m 30 -X POST https://lanfengai.cn/v1/chat/completions -H "content-type: application/json" -H "Authorization: Bearer $(grep ^LLM_API_KEY= .env \| cut -d= -f2-)" -d '{"model":"glm-5.2","max_tokens":8,"messages":[{"role":"user","content":"hi"}]}'`，`200` 为通 |
