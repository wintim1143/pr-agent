## 0. 角色与责任 🟦

| 角色 | 是谁 | 在本里程碑做什么 / 何时介入 |
|---|---|---|
| 触发方 | **调用方显式指定仓库**（HTTP / 验证脚本 / 飞书入口） | M5 **不做**「从 issue 正文让 LLM 猜仓库」—— 路由错误会在**错误的仓库上开 PR**，代价不对称，不该交给模型猜。M5 的触发方**必须显式给出 `repoKey`（`owner/repo`）** |
| 审批方 | **仍为人工**（merge 前 suspend，与 M3/M4 一致） | M5 **不新增人工闸门**，也不放宽既有闸门。多仓库不改变审批语义 |
| 验收方 | **用户（人工）** | ① 看两个靶场各自跑通完整八步；② 手工重投同一条飞书消息，确认不产生第二个 run；③ 手工重跑同一 issue，确认不产生第二个 PR |
| 卡 Owner | 当前开发会话 | 推进并更新本卡 |

> **✅ 待拍板项（2026-09-16，建卡时提出，开工前需用户确认）**
> 1. **去重状态的存储位置** → 建议 **复用 `mastra.db` 同库、建自有业务表**（表名加前缀如 `pr_agent_*`，避免与 LibSQLStore 内部表冲突），
>    而不是新建 `state.db`。理由：单文件即完整可备份状态；且去重**需要原子性**（两个并发 poll 不能都认领同一 messageId），
>    SQLite 的 `INSERT OR IGNORE` + 唯一主键提供了免费且正确的原子认领原语 —— **JSON 文件或内存 Map 做不到这件事**（它们没有跨进程原子性）。
>    ⚠️ 用 `@libsql/client` 直接访问（已是 `@mastra/libsql` 的传递依赖），**不引入新的原生依赖**。
> 2. **多仓库并发的隔离策略** → 建议 M5 只做**「每仓库串行」（互斥锁）**，**明确不做** `git worktree` 级隔离（列入 §3 不做项）。
>    理由见 §3 的风险说明 —— 这是 M5b 最容易被漏掉的真问题，必须显式取舍而不是默默不处理。
> 3. **向后兼容回退** → 建议 `repoRoot(target?)` / `getGithubConfig(target?)` 均吃**可选** target，**缺省回退到现有 env 行为**。
>    好处：M1–M4 的验证脚本与单仓库模式**零改动继续可用**，M5 可以增量推进而不是大爆炸。

## 1. 目标（一句话）🟦

**让同一个 pr-agent 实例能服务多个仓库 —— 触发方显式给出 `owner/repo`，全链路的仓库定位（分支基线 / 红线 / 测试执行目录 / push 目标 / PR 目标）都由该 target 决定而非全局 env；同时把「重复触发」从入口层挡住，使同一事件重投、同一 issue 重跑都不产生重复的 run 与 PR。**

### 核心设计：两个层次，两种幂等键（M5a 的灵魂）

「防重复」有两层语义，**混为一谈会导致只做了一半还以为做完了**：

| 层次 | 幂等键 | 现状（2026-09-16 侦察） | M5a 要做什么 |
|---|---|---|---|
| **入口层** | 事件 ID（飞书 `messageId`） | ❌ **缺口**。`api.controller.ts:82` 自认「真实去重应在持久化游标上做，此处为最小实现」（当前只过滤空消息） | **要做的唯一一件事** |
| **产物层** | 分支名 / PR head | ✅ **M3 已完成**。`github.ts:611-617` 先查同 head 的 open PR 再复用；`github.ts:500` 复用既有分支 | 不动，仅**补 AC 断言**（回归保护） |

> **为什么入口层缺口是真问题而不是洁癖**
> `api.controller.ts:70` 的 `sinceTs` 默认取 `now - 3600`（一小时窗口）。若把 `feishu-poll` 挂上定时器（每分钟一轮），
> 则**同一条消息在一小时内会被重复触发几十次** → 几十个 run → 几十个分支 → 几十个 PR。
> 产物层虽然会复用分支与 PR，但 **run 会重复跑 coding 与 review**（真金白银的 LLM 调用 + 本地工作树争用），
> 且多个 run 同时对同一仓库操作会触发 §3 的并发风险。
> 所以入口层去重的价值不只是「少几个 PR」，而是**避免重复消耗与并发污染**。

### 核心设计：target 里存什么、不存什么（M5b 的灵魂）

| 字段 | 存进 ContextSchema？ | 理由（第一性原理） |
|---|---|---|
| `owner` / `repo` | ✅ 存 | **逻辑标识**，跨机器稳定，是业务语义 |
| `baseBranch` | ✅ 存 | 业务语义；且**红线依赖它**（读错红线会静默失效，M3 已踩过 base 改名） |
| `localPath`（本机 clone 路径） | ❌ **不存** | ⚠️ **ContextSchema 会被序列化进 `mastra.db` 的 snapshot**。M3-5 已实证跨进程 resume 靠快照恢复上下文 —— 把本机绝对路径写进快照，换台机器 resume 就会指向不存在的目录。**本机事实不属于业务流程状态**，应由「仓库注册表」在运行时解析 |

> 这条是本里程碑最容易做错的地方：直觉上「把 target 完整塞进上下文」最省事，
> 但它会让 run 快照**绑定到某台机器的文件系统**，直接破坏 M3-5 挣来的跨进程能力。

## 2. 为什么现在做（排序理由）🟦

| 理由 | 说明 |
|---|---|
| **M4 已把执行器做成仓库无关** | `adapters/test-runner.ts` 的 `runTests(root)` 只吃一个路径参数，`discoverTestFiles()` 也不走 git —— 多仓库的第一块砖 M4 已经砌好，现在接最省力 |
| **M3-6 已把红线参数化** | `guard.ts:121,269` 的 `protectedBranches` 已是注入参数（不再是写死的 `main\|master`）。多仓库所需的红线隔离**已具备接口**，只差调用方按 target 传入 |
| **当前是「5 处 env 读点」写死单仓库** | `CODING_REPO_ROOT` / `GITHUB_OWNER` / `GITHUB_REPO` / `GITHUB_BASE_BRANCH` 被 3 个文件以模块级方式读取，**没有参数化的口子**。再往后拖，调用点只会更多 |
| **入口幂等是「上定时就爆」的定时炸弹** | 现在没爆只因为 poll 是手动打的。触发条件是单一的、已知的（一旦接调度或接事件推送回调），修的成本却很低 —— 典型的「现在修最便宜」 |
| **用户已拍板范围** | 「只做 M5a + M5b」（2026-09-16）。GitHub App 拆出，避免里程碑膨胀 |

## 3. 范围 / 明确不做 🟦

**做**

- **M5a-1 去重存储**：幂等键 + **原子认领**（唯一索引 + `INSERT OR IGNORE` 判定）+ 游标持久化
- **M5a-2 触发入口收口**：显式调度语义（可开关、可指定窗口）+ 已处理消息的游标推进，重启不重放
- **M5b-1 RepoTarget 抽象 + 仓库注册表**：`owner/repo` → `{ localPath, baseBranch }` 映射，配置外置且不入库（含本机路径）
- **M5b-2 target 进 ContextSchema**：**只存逻辑标识**，不存本机路径（见 §1）
- **M5b-3 仓库相关读点参数化**：**17 个调用点 / 4 个文件**（清单见 §7 M5b-3），并含**红线 per-target**
- **M5b-4 多仓库并发安全**：每仓库串行（互斥），防止两个 run 争抢同一本地 clone 的分支状态
- **M5b-5 第二靶场构造**：新建第二个靶场仓库，使「多仓库」有可演示的真实对象（单仓库无法验证多仓库）
- **M5b-6 端到端验证 + AC 回填 + 文档同步**

**明确不做**（留给后续里程碑或独立立项）

- ❌ **不做 GitHub App 鉴权** —— 已剔除，理由见卷首「据实修订说明」。PAT 已实测可用，且支持多仓库
- ❌ **不做「从 issue 正文让 LLM 解析目标仓库」** —— 路由错误会在错误仓库开 PR，代价不对称；M5 要求显式指定。若确实需要，属独立的风险项
- ❌ **不做 `git worktree` 级隔离** —— 见下方并发风险说明
- ⚠️ **【必须显式声明的一条风险】本地 clone 是独占资源，分支切换是仓库级全局状态**
  `git checkout` 改变的是**整个工作树**的分支。若同一个仓库有两个 run 并发执行，
  run-A 切到 `feat/1-*` 后 run-B 切走，**run-A 后续的 commit 会落到 run-B 的分支上** ——
  这是静默的数据损坏，不是报错。M4 的 `--path-a/b/c` 是**串行**跑的所以从未暴露此问题。
  M5 的处置：**每仓库串行锁**（同一 repoKey 同时只允许一个 run 进入 checkout→commit 段）。
  worktree 隔离（每 run 一个工作树）能力更强但成本高得多，**明确留给后续**。
- ❌ **不做仓库注册表的热重载**（改配置需重启进程）
- ❌ **不做崩溃 / 强杀后的锁自愈**（实时探测 holder 的 run 是否已终态需要依赖 `mastra.db` 的内部表结构，太脆）。
  当前靠 `REPO_LOCK_TTL_MS`（30min）兜底；⚠️ 注意 **TTL(30min) > WAIT(10min)**，
  所以一次异常退出会让同仓库后续 run **显式失败**而不是等过去 —— 这是刻意的取向（宁可显式失败也不静默双跑），
  代价是「一次崩溃 = 该仓库 30 分钟内不可用」，如实记录
- ❌ **不做 run 追踪 / 成本回写 / 失败告警**（M6）
- ❌ **不做 review comments 的引用校验**（M4 §9 留下的候选，仍待定）
- ⚠️ **【2026-09-16 补记 · 一处「不做项」的定性】本卡【未承接】前几张卡写的「飞书按钮回调（推迟到 M5）」。**
  `M2:19` / `M2:62` / `M3:30` / `M3:72` / `M4:27` / `验证手册.md:93` 共 **6 处**写着「按钮回调属 M5」，
  但**本卡全文没有这一项** —— 因为它与 M5a 做的东西**不是同一条通路**：
  - M5a 做的是**轮询**（主动拉群消息 → **创建** run，解决「重复触发」）
  - 按钮回调是**事件推送**（长连接 / 回调服务器 → **唤醒**挂起的 run，解决「人工闸门回传」）

  两者形态与作用对象都不同，因此这个承诺**顺势漂过了 M5 变成孤儿**。
  → **现已定性移交 [`M8-飞书双向控制.md`](./M8-飞书双向控制.md)**（2026-09-16 建卡、2026-09-17 由原 M7 重切而来；卷首「无主债务收口」块记录了完整来龙去脉）。
  📌 教训已升格为 `README.md` 全局原则 9「**「不做项」不许悬空**」。

## 4. 端到端演示效果 🟦

**一条 issue 显式指定 `owner/repo-A` → 整个八步落在 A 仓库（分支基线、红线、测试执行目录、push、PR 全对）；另一条指定 `repo-B` → 落在 B 仓库；同一条飞书消息重投不产生第二个 run；同一 issue 在 A 上重跑不产生第二个 PR。**

四条可复现的演示路径：

| 路径 | 输入 | 预期 |
|---|---|---|
| **A 多仓库** | 同一实例连续跑 `repo-A` 与 `repo-B` 两个 issue | 两侧各自开 PR 且**互不串台**（A 的 PR 在 A，B 的在 B）；`test:run` 事件的 `command` 指向各自的 `localPath` |
| **B 入口幂等** | 同一 `messageId` 连续投递 3 次 | 只起 **1 个 run**；后两次被判定为已处理并跳过（有可查证据，不是静默丢弃） |
| **C 产物幂等（回归）** | 同一 issue 在 `repo-A` 上跑两轮 | 第二轮**不新建 PR**，复用第一轮的 `prNumber`；且**不因 422 判负终止** |
| **D 并发串行** | 同一 `repo-A` 同时起两个 run | **串行执行**，不出现「A 的 commit 落到 B 的分支」；若有等待，日志中可见等待证据 |

## 7. 任务分解 🟨

### M5a-1 去重存储：幂等键 + 原子认领
- 内容：新建 `src/mastra/adapters/dedup-store.ts`
  - 表结构：`seen_events(key TEXT PRIMARY KEY, source TEXT, seen_at TEXT, run_id TEXT)`
  - **原子认领**：`INSERT OR IGNORE` 后判 `changes()` —— 插入成功 = 本进程认领成功；冲突 = 别的进程/轮次已处理
  - ⚠️ **原子性是不可省的要求**：两个并发 poll 不能都认领同一条消息。**这是选 SQLite 而非 JSON / 内存 Map 的唯一理由**
- 验收：单测（并发两次认领同一 key，只有一次成功）+ 真实重复投递场景

### M5a-2 触发入口收口 + 游标
- 内容：改 `src/controller/api.controller.ts` 的 `pollFeishu`
  - 用 `M5a-1` 对每条消息先认领；认领失败 → 跳过并**记录可见证据**（不是静默丢弃）
  - 游标持久化：把「已扫到的最大时间戳」落库，`sinceTs` 默认从游标读，**不再每次 `now - 3600`**

> 「**重复触发真的被挡住了**」与「**多仓库真的是隔离的**」—— 这两件事的失败模式都是**静默损坏**（重复消耗 / 提交落错分支），
> 而不是报错。所以判据必须是「有没有第二个 run / 有没有串台」这种可数的事实，不能是「看起来正常」。

## 10. 异常与兜底 🟨

> 失败路径在设计期先想清楚。判定条件必须可执行。每条在实施日志要有对应实测记录。

| 已知异常 | 判定条件（可执行） | 降级行为 | 是否阻断 AC |
|---|---|---|---|
| 未知 `repoKey` | 注册表中查不到该 key | **显式抛错**，绝不回退到「当前仓库」或任一默认仓库 | **是**（阻断 AC-4/AC-10） |
| 注册表文件缺失 / JSON 非法 | 读文件失败或解析异常 | **显式抛错**，不降级为空注册表（空表会让所有多仓库场景静默变单仓库） | **是** |
| `localPath` 不存在 / 非 git 仓库 | 目录不存在或缺 `.git` | **显式抛错**（沿用 `repoRoot()` 现有行为，M2 已确立） | **是** |
| 去重存储不可写 | `INSERT` 抛错 | **fail-closed：拒绝起 run**。⚠️ 不可降级为「去重失效但继续跑」—— 那正是要防的重复消耗 | **是**（阻断 AC-1/AC-2） |
| 同仓库并发争抢 | 第二个 run 请求同一 `repoKey` 的锁 | **等待**（有上限）；超上限 → 显式失败并说明「等待超时」 | **是**（阻断 AC-8） |
| 飞书轮询窗口重叠 | 同一时间窗被扫两遍 | 由去重表兜住（不依赖窗口不重叠） | 否（被 AC-1 覆盖） |
| 旧 env 与 registry 同时配置且矛盾 | 两者都给出同一 repoKey 的不同 localPath/baseBranch | **显式报错**，不静默取其一 | **是**（阻断 AC-7） |
| 向后兼容路径 | 未传 target | 回退到现有 env 行为（M1–M4 不变） | 否（AC-6 保护） |
| ⚠️ **闸门判负导致锁泄漏**（2026-09-16 实测补入） | run 在 test / review / commit 判负 `throw` | **必须在该步的 catch 里先 `releaseTargetLock`**（见 `terminateStep`）。原实现只在 `push-open-pr` 的 finally 释放 → 判负即泄漏，后续同仓库 run **白等 `REPO_LOCK_WAIT_MS`（实测 600001ms）后失败** | **是**（阻断 AC-8，已加「终止后无残锁」判据） |
| 进程被强杀（kill -9 / 崩溃） | holder 不再心跳 | 只能等 `REPO_LOCK_TTL_MS`（30min）被抢占。⚠️ 已知残余风险：**TTL(30min) > WAIT(10min)**，所以一次异常退出会让同仓库后续 run 失败而非等过去 —— 这是刻意的（宁可显式失败也不静默双跑） | 否（超出 M5 范围，见 §3 不做项） |

| # | 缺陷 | 现场证据 | 根因 | 修法 |
|---|---|---|---|---|
| 1 | **review / commit 的 diff 取自 pr-agent 自身工作树** | 同一次 run：`test llm:start diffChars=307`（靶场 README 改动，**正确**）；`review llm:start diffChars=8028`（**pr-agent 自己未提交的 M5 改动**）→ 审核者判 `request-changes` 并准确地列出 `package.json`/`src/controller/...` | `buildChangeContext()` 少一个 `target` → `repoRoot()` 回退到**进程 cwd 的 git 顶层** = pr-agent | review / commit 两处补 `inputData.target` |
| 2 | **仓库锁在闸门判负路径上泄漏** | run `9b0d2725…` 在 review 判负终止后，`peekRepoLock()` 仍返回该 holder；紧接着 run `15311fe2…` 的 checkout `waitedMs=600001` → `REPO_LOCK_TIMEOUT`，**白等 10 分钟**；库里同时挂着 A/B 两把残锁（`releaseAllRepoLocks()` 清掉 2 把） | 释放只写在 `push-open-pr` 的 `finally`，而 test/review/commit 三处判负都在它**之前** `throw` —— 原注释「finally 是锁的唯一出口」只覆盖了**本步**的四条出路 | 新增 `terminateStep()`，5 处终止路径（checkout / coding / test / review / commit）统一「先放锁再上抛」 |

> 🔑 **缺陷 1 的方法学价值**：它**不是** M5 引入的 bug，而是 M5 **暴露**的既有 bug ——
> 单仓库模式下 `CODING_REPO_ROOT` 总被设着，回退恰好命中正确仓库，所以 M1–M4 四轮都看不见。
> **去全局化会把所有隐式回退变成显式错误**，这是「多仓库」超出功能本身的收益。
> 同理，`repoRoot()` 的回退兜底（`cwd` 的 git 顶层）在设计期看起来是「方便的向后兼容」，
> 实测证明它是**「在错误仓库上开 PR」的结构性入口**。

- **本轮核实的新事实（源码级）**
  1. **「串行有效」≠「释放完整」**：锁机制正确 ≠ 每个终止出路都放锁。判据必须**分别可数**：
     「有没有等 / 有没有串台」（AC-8 前半）与「run 结束后锁是否已释放」（AC-8 后半，实测补入）。
     只验前者会得到一个**全绿的泄漏系统**。
  2. **闸门判负是「常见出路」而非「异常」**：M4 的主题就是判负，因此**每一条判负路径都会被执行**。
     任何「只在正常路径收尾」的清理逻辑（放锁 / 释放资源 / 落审计）都会在 M4 时代起频繁泄漏。
  3. **`z.toJSONSchema()` 才能验 schema 形状**：`ContextSchema.shape.target.shape` 取不到
     （`ZodOptional` 没有 `.shape`）→ 必须 `z.toJSONSchema(ContextSchema).properties.target.properties`。
     ⚠️ 副作用提醒：`target` 不能用 `.refine()`，否则无法转 JSON Schema（schema 同时是 workflow `inputSchema`）。
  4. **`git fetch` 不更新 `refs/remotes/origin/main`**（PortableGit + sandbox 的老毛病，同 `git commit` 不写 ref）：
     靶场 A 出现「本地 main 领先 origin/main 2 个提交」的假象，但 `git ls-remote origin refs/heads/main`
     确认远端就是 `21f4e7a`。**判远端状态一律用 `ls-remote` / REST，不要信 remote-tracking ref。**
  5. **`npm run build` 在本会话不可靠**（退出码 1 + `?????` 乱码输出，且 sandbox 会拦它顺带拉起的 `wsl.exe`）；
     `node node_modules/mwtsc/bin/mwtsc.js --cleanOutDir` 直调稳定成功。同理单测走
     `NODE_ENV=unittest node node_modules/jest/bin/jest.js`。**这类环境差异别误判成代码回归。**
  6. **Token 写权限范围实测**：`POST /user/repos` 空参 → **403**（无建仓库权）；写探针确认只有
     `wintim1143/pr-agent` 与 `wintim1143/pr-agent-e2e` 可写 → 第二靶场 B **只能是纯本地仓库**
     （`stopAfterCommit`，零远端）。这决定了 §4 演示路径「B 不开 PR」不是偷懒而是**凭据边界**。

- **AC-9 的判据修订（自查出的假通过）**
  首版 `--multi` 里 AC-9 写成 `prA2?.prNumber === prA?.prNumber` —— 两轮都失败时
  `undefined === undefined` **恒真**，是一处**假通过**（与 M4「`node --test` 零文件 exit=0」同构）。
  修法不是加 `!== undefined` 了事，而是换判据来源：AC-9 的本质是 `openPrForBranch()` 的**纯程序行为**，
  所以**主判据改为确定性探针**（同一 head 再调一次 `githubPushAndOpenPR` → 必须复用同一 `prNumber`；
  若复用退化，第二次会真发 `POST /pulls`，GitHub 回 **422 already exists**）。
  端到端两轮对比降级为**附加观察**，仅在两轮都真 push 时才判定 —— 因为它混进了 review 闸门的 LLM 判断。
  > 实测：A#1 因「全角冒号 vs 半角」被判 `request-changes`（判得**对**，diff 里确实混用了），
  > 于是首版 AC-9 直接失去判定对象。**只要判据里混进 LLM 的非确定性，就必须有一条确定性的主判据。**
