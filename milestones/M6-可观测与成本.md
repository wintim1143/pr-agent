## 1. 目标（一句话）🟦

**把「已经打了很多、但关联不起来」的日志升级为可关联的运行追踪 —— 每个事件带真实 `runId` 与阶段，能按 run 重建八步时间线、算出耗时与 token 花费、并把失败定位到具体的 run 与 step。**

## 2. 为什么现在做（排序理由）🟦

| 理由 | 说明 |
|---|---|
| **债已到临界点，且已实测确认** | `runId` 字段在 `progress.ts:85` 已声明，但 701 条事件里**真实覆盖率 = 0/701**。唯 6 条带 `runId` 的记录，值是字面量 `"rejected"` / `"resumed"`（见 §11 已核实事实）。**多 run 事件在同一文件里交错，无法按 run 分组** |
| **它是 M8 的前置，不是可选优化** | 飞书卡片按钮回调的本质是「用一个标识定位到某个挂起的 run 并 resume」。现在 dev 卡片的按钮 value 是 `merge_<issueNumber>`（`adapters/feishu.ts:169-170`），**在多仓库 + 重跑场景下不唯一**（同一 issue 可多次 run，A/B 两个靶场可有同号 issue）。**没有可靠的 runId 贯穿，M8 的回调就是猜**（⚠️ 2026-09-17 更正：原写作 M7；**M7 只做对话，不依赖 M6**） |
| **成本无归口，答不了「哪个仓库最烧钱」** | 现有事件只有 `llm:start` / `llm:done` / `attempt`，**没有任何 token 或金额字段**。而每个 run 都在真金白银地跑 coding + review（M5a 的立项理由之一就是这个） |
| **收前卡明确挂账的债** | M2 §3、M3 §3、M4 §3、M5 §3 **四处**都写着「不做 run 追踪 / 成本回写 / 失败告警（M6）」。这是唯一一张被四个里程碑点名欠账的卡 |
| **顺手清一处文档幻觉** | `M1-只读洞察闭环.md:90` 的模块表写着 `Logger`（`@mastra/core/logger`）「每步打点」，但 **`src/` 里零 import** —— 建卡时的预期被写成了事实。M6 要么真的用它，要么把那一行改对 |

## 3. 范围 / 明确不做 🟦

### 做

- **M6-1 统一日志规范（成文 + 落地）**
  1. 新增 `docs/日志规范.md`：**哪些输出必须落文件** / **什么级别** / **字段命名与必填** / **禁止事项**。
     把事实约定 `[stage-name] message`（阶段名 = 八步）**升格为规范**，不另造一套。
  2. 新增统一 logger 模块（扩展 `progress.ts` 或在其旁新建 `logger.ts`），**收编现有 35 处裸 `console.*`**：
     `dev-workflow.ts` 19 / `insight-workflow.ts` 8 / `config.ts` 2 / `inbound-poll.ts` 2 /
     `coding-agent.ts` 1 / `progress.ts` 3（其中 3 处是 logger 自身与「写日志失败」告警，可保留）。
  3. 原则：**「有意义」的输出一律落文件**（结构化），console 只作为**人看的那一份镜像**，
     不允许「只打 console 不落盘」。
- **M6-2 `runId` / `traceId` 穿线（本里程碑的技术核心）**
  - `stageStart()` / `stage()` 的**位置参数改对象参数**：`stageStart({ stage, runId })`。
    依据：现在签名是 `stageStart(stageName: string, runId?: string)` —— **两个都是 string，传错编译器不报错**，
    这正是 `'rejected'` / `'resumed'` 溜进 `runId` 槽的结构性原因。改成对象参数后，误用变成**编译错误**。
  - 每个 step 从 execute 上下文取真实 `runId`（Mastra 已经给了：`execute: async ({ inputData, runId })`），
    向下传给所有 `stage()` 调用点。缺口点在：`merge` 步**没有解构 runId**（`dev-workflow.ts:1081`）。
  - 提供 `traceId` 语义：**runId 为 run 级 trace，`<runId>:<stage>` 为 step 级 span**。
    ⚠️ 字段命名按 OTEL span 语义（start / end / durationMs）保持可迁移，见 §6 选型。
- **M6-3 日志分片与保留**
  - 方案二选一（§0 待拍板）：**(a) per-run 文件** `logs/runs/<runId>.log`（分离度最好，但 run 中途崩溃时要知道文件名）；
    **(b) 单文件 + `runId` 字段 + 提供 `queryByRun(runId)` 读取器**（改动最小，向后兼容现有 701 行历史）。
  - 补**轮转**：当前 `logs/dev-workflow.log` 单文件追加、无轮转、已 100KB 且含 9-14 起的全部历史。
- **M6-4 成本回写**
  - `llm:done` 事件补 `usage`：`promptTokens` / `completionTokens` / `totalTokens`（中继返回什么就记什么，
    拿不到就记 `null` —— **不可等价于 0**，与 M4「`testsPassed=null` ≠ `true`」同构）。
  - 按 `target.repoKey` 聚合，能回答「哪个仓库花了多少 token / 多少次 LLM 调用」。
- **M6-5 run 终态与失败可见**
  - 每次 run 落一条 `run:end`：`runId` / `target` / `status` / 总耗时 / 失败步 / 失败原因。
  - 让 M5 已能观测到的三处不对称**变成可判据**（见 §11）：每 `(runId, stage)` 的 `start` 数 === `done + fail` 数。
- **M6-6 验证脚本 + AC 回填 + 三处文档同步**

### 明确不做（留给后续里程碑）

- ❌ **不引入 OTEL / 观测后端**。依据：本项目当前**没有观测后端**，`progress.ts:22-26` 的注释已论证过
  「写本地文件的收益（零依赖、可直接 `tail`）更直接」；且 M6 的判据是**可关联**，不是**可上报**。
  字段按 span 语义命名即为将来的迁移留口。等真出现多实例 / 多机分布式追踪需求再上。
- ❌ **不做前端 dashboard / 可视化**
- ❌ **不做跨机器聚合**（单机单实例足够）
- ❌ **不接飞书 inbound / 按钮回调** —— **M8**（M7 只做对话，同样不接按钮回调）
- ❌ **不改八步拓扑、不改判据归属**（M4 的 `testsPassed` 归程序 / `requirementMet` 归 LLM 一律不动）
- ⚠️ **一处已知的、本里程碑不解决的观测盲区**（诚实记录）：
  agent 侧（Claude Code CLI 子进程）内部发生了什么，本项目依然看不到 —— 只能看它返回的结果。
  真要进入需要解析 `~/.claude/projects/<repo>/*.jsonl`，属独立议题。

## 4. 端到端演示效果 🟦

**跑一次 `--multi`（或任意一次真实 run）后，用一条命令从日志里重建出：**

```
$ node scripts/verify-m6-observability.js --report <runId>
run <runId>  target=wintim1143/pr-agent-e2e  status=ok  总耗时 215.4s
  checkout      12.1s
  coding       117.3s   llm×4   1,842 tok

  commit        34.2s   llm×1     248 tok
  push-open-pr  10.0s
  notify         0.8s
```

再按 `checkout step:start` 在混杂日志里手工切分（这条手法记在 `.workbuddy/memory/ref-ops.md`）——
**M6 就是把这条手工手法消掉。**

## 5. 数据流向图 🟨

**数据流向图文件**：[`M6-可观测与成本-flow.md`](./M6-可观测与成本-flow.md)

```
触发(脚本/HTTP) → createRun().start()
                    │  runId 由 Mastra 生成
                    ▼
   ┌─────────────────────────────────────────┐
   │ dev-workflow  八步（拓扑不变）           │
   │  checkout → coding → test → review →    │
   │  commit → push-open-pr → notify → merge │
   │     每个 step 的 execute 上下文里有 runId │ ← 【M6-2 的取数点】
   └────────────────┬────────────────────────┘
                    │  stageStart({stage, runId}) / stage({..., runId})
                    ▼
        ┌──────────────────────────┐
        │  logger（M6-1 统一出口）  │
        │  · 结构化记录（真源）     │
        │  · console 镜像（人看）   │
        └───────────┬──────────────┘
                    ▼
      logs/runs/<runId>.log  或  logs/dev-workflow.log(+runId)
                    │
                    ▼
   verify-m6-observability.js --report <runId>
     → 按 run 重建时间线 / 聚合 token / 校验 start↔end 配对
```

**与 M5 的差异**：M5 只要求「事件存在且可 grep」；M6 要求「事件**可按 run 分组**且能重建时间线」。
断点位置（`suspend` / `resume`）不变，但 resume 前后的事件必须落在**同一个 runId** 下 —— 这是 M8 按钮回调的判据基础。

## 6. 用到的 Mastra 模块（本里程碑重点）🟨

> 本节只写选型结论 + 取舍理由，源码行号归 §11。

| Mastra 模块 | 导入路径 | 职责 | 为什么用它，而不是裸写 |
|---|---|---|---|
| `createStep` 的 execute 上下文 | `@mastra/core/workflows` | **提供 `runId`**（每步都有） | 这是「runId 穿线」的**免费取数点** —— 不需要自己发明 trace 传递机制。Mastra 已经把它放进了每个 step 的入参 |
| `run.runId` / `createRun()` | `@mastra/core/workflows` | run 标识来源 | 与 `mastra_workflow_snapshot` 表、M5 的 dedup `run_id` 列、锁的 `holder` **同一套标识** —— 全链路已有交叉引用能力，M6 只是把它接进日志 |
| `LibSQLStore`（`mastra_workflow_snapshot`） | `@mastra/libsql` | run 快照 / 跨进程 resume | M6 **不替换它**，只要求日志不再需要反查它。⚠️ 不去读它的内部表结构做实时查询 —— M5 §3 已判定「太脆」 |
| `Logger`（`@mastra/core/logger`） | `@mastra/core/logger` | 候选统一日志出口 | ⚠️ **需实测评估**：M1 卡写着用了它，实际**零 import**。§0 待拍板项之一：**用 Mastra Logger 做出口，还是继续自建 `progress.ts` 演进** |
| `@midwayjs/logger` | `@midwayjs/logger` | 候选统一日志出口 | ⚠️ **当前是依赖但基本空转**：`logs/my-midway-project/` 下 `common-error.log.*` / `midway-core.log.*` **全 0 字节**，`midway-app.log` 只有 20 行框架路由加载。说明代码的 `console.error` 一条都没进框架 error log |

**选型备注（三选一的判据）**：
- **自建 `progress.ts` 演进**（推荐倾向）：零迁移成本、字段已按 span 语义命名、现有 701 行历史格式兼容、验证脚本已依赖它。
- **Mastra `Logger`**：若它原生支持结构化字段 + 文件输出，可省自建；但需先实测其输出格式与轮转能力，
  且要处理「M1 卡说用了、实际没用」这处不一致。
- **`@midwayjs/logger`**：框架自带、有按天轮转；但它是**应用级** logger（面向 Web 请求），
  与本项目「run 级 trace」的维度不匹配 —— 除非确认它支持任意结构化字段。
- 📌 无论选哪个，**判据不变**（§8）：可关联、可重建时间线、字段语义可迁移。

- 内容：`stageStart` / `stage` 改对象参数；八步全部传真实 `runId`（补齐 `merge` 步的解构）；

- 验收：日志里**除进程启动期事件外**所有事件带非空 `runId`；且 `runId` 取值**不得等于**

- **实做**：改**对象参数**（`stageStart({stage, runId})`）—— 让「位置参数塞错」**无法通过编译**，这是本里程碑最关键的一处结构性修改；

  `runId === null` 且阶段不在 `RUNLESS_STAGES` → 落 `trace:missing`。八步 + `insight-workflow` + `config` + `inbound-poll` 全部穿线。

### M6-3 日志分片与保留 ✅
- 内容：按 §0 拍板结果实现 per-run 文件或 `queryByRun()` 读取器；补轮转与保留策略。
