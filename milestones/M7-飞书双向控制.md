## 0. 角色与责任 🟦

| 角色 | 是谁 | 在本里程碑做什么 / 何时介入 |
|---|---|---|
| 触发方 | **飞书群里的成员** | 在群里 @bot 发一句话（**必须带显式仓库标识**，见 §3 M7-2）。机器人取代了 curl / 验证脚本成为主入口 |
| 审批方 | **群内的人，点卡片按钮** | 卡片上的「🔀 合并 / ❌ 拒绝」按钮 → `card.action.trigger` 回调 → resume。**这是本里程碑的核心交付**，取代现在的「手工打 HTTP resume 端点」 |
| 验收方 | 开发者本人 | ① 在真实飞书群里走一遍完整链路；② 跑验证脚本验边界（未授权用户 / 未知仓库 / 重投 / 并发）。**脚本能证明的极限是「回调被正确处理」，不能证明「群里真的收到了」** —— 后者必须人工看一眼 |
| 卡 Owner | 当前开发会话 | 推进 + 更新本卡 + 三处同步 |

> ⚠️ **准入是安全边界，不是可选项**：一旦群里的人能让 agent 在真实仓库上跑代码并开 PR，
> 「谁有资格触发」就必须显式定义（§0 待拍板项 5）。默认**不能**是「群里任何人」。

## 2. 为什么现在做（排序理由）🟦

| 理由 | 说明 |
|---|---|
| **这才是这个项目的产品形态** | M1–M6 一直是在「把链路做对」（只读 → 本地写 → 真 PR → 真闸门 → 多仓库 → 可观测）。**IM 驱动本身才是目的**，所以 M1 就把飞书入口提前做（曾是后置项 S5）。现在链路已经对了，缺的是**入口** |
| **无主债务到期（见卷首）** | 按钮回调被四处承诺、无人承接。**不主动立项，它会继续漂到 M8** |
| **前置已被 M5 解掉** | 「多人从群里触发」会带来两个必然问题，M5 恰好都提前修了：① **重复触发** → 入口幂等（唯一索引原子认领 + 游标）；② **同仓库并发导致提交落错分支** → 每仓库串行锁。**M5 的立项理由里写的就是这个场景** |
| **观测前置由 M6 解掉** | 按钮回调的本质是「**用一个标识定位挂起的 run 并 resume**」。M6 之后卡片才能携带可信 `runId`（现状见 §3「已核实的缺口」） |
| **⚠️ 不做的话，剩下的能力全是「半自动化」** | 现在每一步都要人手工喂入参、手工 resume。工具做了六轮，仍然不是「能用的东西」 |
| **⚠️ 为什么是「M6 之后」而不是「替代 M6」** | 见下方「排序论证」。**一句话**：先做飞书会得到一个**能跑但无法验收**的里程碑 |

### 排序论证：为什么飞书是 M7 而不是 M6

> 这是本卡最容易被反复追问的一条 —— 因为「**通过飞书控制这个项目**」是用户的真实目标，
> 直觉上「最想要的该最先做」。但顺序不由「谁重要」决定，由**谁阻塞谁**决定。

| # | 论证 | 事实底座 |
|---|---|---|
| 1 | **回调能力的前提是「可信标识」，而标识现在不可信** | 回调 = `resume(runId)`。现状：日志 `runId` 覆盖率 **0/701**（唯 6 条是 `'rejected'` / `'resumed'` 污染值）；卡片标识是 `merge_<issueNumber>`（多仓库下必然撞号） |
| 2 | **先做飞书会得到「能跑但不能验收」的里程碑** | 本卡**核心判据 AC-4**（回调定位到正确的 run、只有 A 被 resume）只能靠「构造双 run + **查日志确认**」来验 → **没有 runId 贯穿，这条判据根本执行不了**。能点通按钮 ≠ 验得出来点对了 |
| 3 | **依赖单向，顺序没有选择余地** | M6 的全部工作作用在**既有链路**上（insight / dev 两条 run 都能独立跑）；M7 依赖 M6 的产物。反向做就得造临时标识来验回调，验完再拆掉 |
| 4 | **先做飞书 = 返工** | 卡片 value 会先做成 `merge_<issueNumber>`，M6 做完还得回头改卡片。M6 先做则一次做对 |
| 5 | **两者验收方式不同，合并会无法统一收口** | M6 判据**全部可程序判**（有 runId 的事件可数 / `step:start` 配对可数 / run 终态可数）；M7 判据需**真人 + 真群 + 真网络**（长连接韧性 / 真按钮真 merge）。并成一张卡 → 「一半靠脚本、一半靠人在群里点」，给不出单一通过标准 |
| 6 | **外部未知不该污染确定性** | M6 新增外部依赖 = **零**。M7 有**两个未实测的外部未知**：① 本机无公网入口 → 必须长连接，而 `@larksuiteoapi/node-sdk` **是否支持 `card.action.trigger` 尚未实测**；② `im:message.group_msg` 读权限 M1 实测**是缺的**（`code=230027`）。放进 M6 会让「M6 能不能过」取决于飞书那边 |

> 📌 **「立项」与「开工」是两件事。** 本卡 2026-09-16 就建了，但建卡不构成「插队」的理由 ——
> 立项是为了**把 6 处悬空承诺定性、把范围锁死**（执行 `README.md` 全局原则第 9 条「不做项不许悬空」），
> 不是为了提前执行。**建卡防漂移，顺序按依赖。**
> 📌 **M6 也不是纯为 M7 铺路**：成本回写、失败重试告警、`repo:lock` 泄漏这类不对称的可观测，自身就是收益。

## 3. 范围 / 明确不做 🟦

### 已核实的缺口（动手前已实测，决定了本里程碑的真实工作量）

| # | 缺口 | 一手证据 |
|---|---|---|
| 1 | **飞书入口只起 `insight-workflow`（只读洞察），从来不起 `dev-workflow`（真开发）** | `src/controller/api.controller.ts:89-94` 的 `startRun` 硬编码 `mastra.getWorkflow('insight-workflow')`。**`dev-workflow` 至今只能被验证脚本启动** |
| 2 | **一句话喂不进 `dev-workflow`** | `ContextSchema`（`dev-workflow.ts:168-222`）要求 `issueNumber` / `issueTitle` / `issueBody` / `target{owner,repo,baseBranch}`。飞书一句话**没有这些字段** |
| 3 | **按钮 value 无法唯一确定一个 run** | dev 卡片用 `merge_<issueNumber>` / `reject_<issueNumber>`（`adapters/feishu.ts:169-170`），而 insight 卡片用 `confirm_<runId>`（`insight-workflow.ts:182-183`）—— **两套不兼容的回调标识**。多仓库 + 重跑下，issueNumber **不唯一**（同一 issue 可多次 run；A/B 两个靶场可有同号 issue） |
| 3b | **标识把两个正交维度压成了一个字符串** | `merge_<n>` 同时承载「**哪个 run**」（身份，用于**定位**）与「**哪个动作**」（意图，用于**分支**）—— 两者消费方式不同，不该编进同一 token。⚠️ 与 M6 侦察出的 `stageStart('merge','rejected')` **同构**（语义串塞进 `runId` 形参，两形参都是 string → 编译器拦不住）。**2026-09-17 拍板：改为结构化 value**，见 §3「做」M7-4 与 §7 |
| 4 | **卡片不显示目标仓库** | `buildDevCompleteCard(ctx)` 只收 `issueNumber` / `issueTitle` / `branch` / `prNumber` / `prUrl` —— **无 target**。多仓库下群里只看到「PR #5」，不知道是哪个仓库的 |
| 5 | **无长连接能力** | `package.json` 依赖里**没有** `@larksuiteoapi/node-sdk`；现有 `feishuListMessages` 是**轮询**（`adapters/feishu.ts:261`）。本机在家庭网络**无公网入口** → 事件推送必须走长连接（或内网穿透） |
| 6 | **收消息权限可能仍缺** | M1 实测 `code=230027`（缺 `im:message.group_msg` 读权限）→ 当时降级为「仅发不收」。`adapters/feishu.ts:251-252` 仍标注该前置 |
| 7 | **人工闸门只能手工触发** | 现在靠 `POST /api/workflows/<wf>/resume?runId=xxx`（`@mastra/koa` 自带）。M3 的卡片文案已如实写「按钮点击无效」（`feishu.ts:157-159`） |

> ✅ **有利条件**：`.env` 里 **`FEISHU_APP_ID` + `FEISHU_APP_SECRET` + `FEISHU_RECEIVE_ID` 均已配置**
> → 走的是**自建应用模式**（不是 webhook 机器人），而 `card.action.trigger` 回调**只有自建应用才支持**。
> 即：**飞书侧的责任边界已具备，缺的是本机侧的接收端**。

### 做

- **M7-1 事件接收通道（长连接）**：接 `im.message.receive_v1`（收消息）+ `card.action.trigger`（收按钮回调）。
  本机无公网入口 → 走飞书官方**长连接**（WebSocket），避免内网穿透；
  ⚠️ 若长连接不支持卡片回调，则降级为「内网穿透 + 回调 HTTP 服务器」—— **§0 待拍板项 1**。
- **M7-2 约束式自然语言路由（安全关键）**
  - 群里一句话必须**显式指定仓库**（语法待定：`[repo-A]` 前缀 / `@repo-A` 提及）。
  - **解析失败 → 拒答 + 回卡片提示，零 run 起**。**绝不回退到「当前仓库」或默认仓库** ——
    路由错误的代价不对称（会在**错误的仓库**开 PR），这与 M5 §3「不做从 issue 正文让 LLM 解析目标仓库」同一理由。
  - 解析结果必须过**仓库注册表白名单**（`repoKey` 存在性校验）。
- **M7-3 入口从 insight 分流到 dev**：群里一句话 → 起 `dev-workflow`。
  `insight-workflow` 保留为**独立命令**（如带 `?` 前缀只做洞察），不混在一句话里猜。
- **M7-4 卡片按钮回调 → resume**：value 改为**结构化 JSON 对象**（**2026-09-17 拍板，不用任何分隔符**）：
  dev 卡片 `{ kind:'dev', action:'merge'|'reject', runId, repoKey }` /
  insight 卡片 `{ kind:'insight', action:'confirm'|'rerun', runId }`。完整定义见 §7 M7-4。
  依据：① **`runId` 全局唯一** → 一次解决缺口 3 的「多仓库 + 重跑不唯一」问题（这是 M6 runId 穿线的下游价值）；
  ② **结构化从根上消掉缺口 3b** —— 没有拼接就没有分隔符可争论。
  回调侧：`createRun({ runId })` 重建 run 对象后 `resume({ approved })`（M1/M3 已实证跨进程可行，靠 LibSQLStore）。
- **M7-5 卡片补 target 与 runId**：卡片正文显示**仓库名 + base 分支 + runId**（可点击/可复制，便于人拿 runId 去查日志）。
- **M7-6 常驻化**：把「手动打 poll 端点」变成常驻进程（长连接天然常驻）；优雅退出；**重启不重放**（复用 M5a 游标）。
- **M7-7 准入控制**：触发者/审批者的身份校验（白名单 user_id 或群成员校验），未授权 → 拒答 + 落审计事件。
- **M7-8 验证 + AC + 三处文档同步**

### 明确不做（留给后续里程碑或独立立项）

- ❌ **不做 GitHub App 鉴权** —— 与飞书无关，`README.md` 已把它列为独立后置项（M5 时剔除）；
  只有在要做 **webhook 推送式**触发时才是前置，而本里程碑走长连接，**不需要**
- ❌ **不做多租户 / 多群隔离** —— 单实例单群，够用；多群会让「仓库白名单」变成「群 × 仓库」二维矩阵，复杂度不成比例
- ❌ **不做卡片上的多轮对话式交互** —— 只做两个**确定性动作**（合并 / 拒绝）。自由文本回复会引出一整套「对话状态机」，属另一个项目
- ❌ **不做 `git worktree` 级并发隔离** —— 沿用 M5 的每仓库串行锁（见下方风险）
- ❌ **不改闸门判据归属、不改八步拓扑**
- ⚠️ **必须显式声明的两条风险**：
  1. **并发压力上升**。群聊里多人同时说 → 同仓库 run 会**排队**（M5 串行锁）。
     且 M5 已知 **`REPO_LOCK_TTL_MS`(30min) > `REPO_LOCK_WAIT_MS`(10min)** ——
     一次异常退出会让该仓库**显式失败**而非等过去。现在这个窗口会**被真实撞上**（不再是理论值）。
     → 本里程碑应把这两条从「已知残余风险」升格为**需要观测的量**（依赖 M6 的日志）
  2. **触发即执行 agent 写下的代码**。准入（M7-7）不是锦上添花 —— 它决定了「谁能让 agent 在真实仓库上跑代码并开 PR」

## 4. 端到端演示效果 🟦

**在飞书群里发：**

```
[pr-agent-e2e] 给 README 加一节「快速开始」
```

**看到：**

1. 群里回一张卡片：`🚀 已启动 · 仓库 wintim1143/pr-agent-e2e · 分支 feat/… · runId <runId>`
2. 几分钟后同一张卡片更新为开发完成：**仓库名 + 分支 + PR 链接**（不再是光秃秃的 `#5`）
3. 点「🔀 合并」→ PR 被真 squash 合并，卡片更新为已合并
4. （或点「❌ 拒绝」→ run 到终态、PR **保持 open**，可由人工处置 —— 沿用 M3 已有的拒绝语义）

**四条可复现的演示路径：**

| 路径 | 输入 | 预期 |
|---|---|---|
| A 正向闭环 | `[repo-A] 给 README 加一节快速开始` | 起 dev run → 卡片含仓库名/分支/PR 链接 → 点合并 → PR 真 merged |
| B 路由拒绝 | `帮我改点东西`（**无仓库标识**） | **零 run 起**，回卡片「请指明仓库（可用：repo-A / repo-B）」 |
| C 回调隔离 | 点 A 卡片上的按钮 | 只 resume **A 那个 run**；同群 B run 不受影响（多仓库下不串台） |
| D 重投幂等 | 同一条飞书消息被长连接重投 2 次 | 只 1 个 run（复用 M5a 去重表，`source=feishu:<chatId>`） |

## 6. 用到的 Mastra 模块（本里程碑重点）🟨

> 本节只写选型结论 + 取舍理由，源码行号归 §11。

|---|---|---|---|
| `createRun({ runId })` | `@mastra/core/workflows` | **按 runId 重建 run 对象**（回调侧的核心） | 回调是独立 HTTP 请求，手里只有 runId。M1 已实证可行；M3-5 已实证**跨进程**可行。**这是「按钮能点」的技术底座** |
| `run.resume({ approved })` | `@mastra/core/workflows` | 唤醒挂起的 run | 与 M3 的人工闸门**同一条路径**，只是触发方从「手工 HTTP」变成「飞书回调」—— 语义零变化，风险可控 |
| `LibSQLStore`（`mastra_workflow_snapshot`） | `@mastra/libsql` | 跨进程 resume 的持久化前提 | ⚠️ 必须配。不配 storage 时按 runId 重建 run 再 resume 会报 `This workflow run was not suspended`（M1 `index.ts` 的注释已记录此坑） |
| `Integration` 基类 + `createTool` | `@mastra/core/integration` / `@mastra/core/tools` | 飞书 client / 工具集 | 已在 M1 落地（`integrations/feishu.ts`），本里程碑**只扩展不重写** |
| `Workflow` / `createStep` | `@mastra/core/workflows` | 八步编排 | **不改拓扑**。M7 的改动全部落在**入口侧与回调侧**，编排层不动 |

**选型备注**：
- **飞书长连接**：候选 ① 官方 `@larksuiteoapi/node-sdk`（`WSClient`，飞书官方维护、封装重连与签名）；
  ② 自写 WebSocket 客户端（零新依赖，但要自己实现握手/心跳/重连/签名，**不划算**）。
  → **倾向 ①**，但需实测它是否同时支持 `card.action.trigger` 回调（**§0 待拍板项 1**）。
- **不用内网穿透**：`ngrok` / `frp` 之类会引入外部依赖 + 一个公开暴露的端点，而长连接不需要公网入口。

## 7. 任务分解 🟨

### M7-1 事件接收通道（长连接）
- 内容：接入飞书长连接，注册 `im.message.receive_v1` + `card.action.trigger` 两个事件；
  实现重连（指数退避）、优雅退出、事件落日志（**复用 M6 的统一 logger**）。
- 验收：能收到群消息与按钮回调（各一条真实事件）；断开长连接后能自动重连；进程可优雅退出。

### M7-2 约束式自然语言路由
- 内容：语法设计 + 解析器（纯函数、可单测）+ 仓库注册表白名单校验；
  解析失败/未知仓库 → **拒答 + 回卡片**，零 run。
- 验收：**单测覆盖 ≥ 8 条**，含 4 条**负向用例**（无仓库标识 / 未知仓库 / 语法残缺 / 只 @bot 不说话）
  断言「**抛错或拒绝，绝不返回默认仓库**」。

### M7-3 入口分流到 dev-workflow
- 内容：`startRun` 按命令类型分流（dev / insight）；「一句话 → `issueNumber`/`issueTitle`/`issueBody`/`target`」的映射
  （**issueNumber 的来源是 §0 待拍板项 2**）。
- 验收：群里一句话真起 `dev-workflow` run；日志出现该 runId 且 `repo:target` 事件里 `repoKey` 正确。

### M7-4 卡片按钮回调 → resume（**2026-09-17 拍板：结构化 value，无分隔符**）

- **value 形态 —— 唯一权威定义，两处产出点必须与之一致**

  | 卡片 | value（JSON 对象） |
  |---|---|
  | dev（`adapters/feishu.ts:169-170`） | `{ kind: 'dev', action: 'merge' \| 'reject', runId, repoKey }` |
  | insight（`workflows/insight-workflow.ts:182-183`） | `{ kind: 'insight', action: 'confirm' \| 'rerun', runId }` |

  | 字段 | 为什么必须有 |
  |---|---|
  | `kind` | 两种卡片的回调**打到同一个长连接接收端** → 必须能分流。旧方案靠前缀（`merge_` / `confirm_`）**隐式**承担了这个职责，结构化了就得**显式**写出来 |
  | `action` | 动作。⚠️ **必须过闭集校验**（zod enum）；未知 action → 拒绝 + 落事件。**禁止 `else` 兜底**（否则未知动作静默走默认分支 —— 与 M4「判据归属」要的严格性同一要求） |
  | `runId` | 定位 run。**`issueNumber` 从此彻底退出回调标识**（它只在单仓内唯一，M5 多仓库后必然撞号） |
  | `repoKey` | 多仓库下的**交叉校验**（防「B 的卡片被当成 A 的回调」）。**只写逻辑标识，本机 clone 路径绝不进卡片**（同 M5 铁律） |

- **飞书侧约束（一手来源已核）**：`value` **仅支持 key-value 形式的 JSON 结构，且 key 为 String 类型**
  → 结构化天然满足，**对字符串内容无字符集限制**。
  ⚠️ `docs/archive/11-IM驱动的多Agent自动开发工作流设计.md:125` 的「`callback_id` ≤128、
  仅字母数字下划线短横线」**查无一手来源，勿引用**（真正的上限是整张卡片的体积）。
- 处理流程：**schema 校验 → `createRun({ runId })` → `resume({ approved })`**；
  **run 已终态 / runId 不存在 / value 非法** 三种都要有明确回执（见 §10）。
- 迁移触点（**本轮不动代码**；留给本任务实施）：`feishu.ts:169-170`、`insight-workflow.ts:182-183`。
  ✅ **迁移窗口已测量**：全仓**无任何解析器**（`split|match|slice|indexOf` 在三处相关文件零命中；
  `test/` 无断言按钮 value 的用例）→ 现在改只需 2 个产出点。
  📌 **教训：约定类改动要抢在「第一个消费者」落地之前做** —— 本任务写完解析器后再改，就是
  「改代码 + 改测试 + 改已发出去的卡片」。
- 验收：点「合并」→ PR 真 merged（可查 GitHub）；点「拒绝」→ run 终态且 PR 仍 open。

### M7-5 卡片补 target / runId
- 内容：`buildDevCompleteCard` 加 `target` / `runId` 参数并渲染；文案去掉「按钮点击无效」的旧说明。
- 验收：多仓库下卡片能区分 A/B（含仓库名与 base 分支）。

### M7-6 常驻化与幂等
- 内容：常驻进程（长连接天然满足）；复用 M5a 游标与去重表（`source = feishu:<chatId>`）。
- 验收：同一条消息重投 2 次 → 只 1 个 run；重启进程后不重放历史消息。

### M7-7 准入控制
- 内容：触发者 / 审批者的身份校验（§0 待拍板项 5）；未授权 → 拒答 + 落审计事件（复用 `guard:deny` 语义或新增 `auth:deny`）。
- 验收：**负向用例**：白名单外的人触发 → 零 run 起 + 有审计事件。

### M7-8 验证脚本 + AC 回填 + 三处文档同步
- 内容：`scripts/verify-m7-feishu.js`（**独立新文件**，不改 `verify-pr-loop.js` / `verify-m4-gate.js` /
  `verify-m5-multirepo.js` / `verify-m6-observability.js`）。
  分层：秒级确定性模式（假事件注入，验路由/回调/准入/幂等） + 一个真飞书模式（人工在群里走一遍）。
- 验收：全部模式通过；卡 §8 无 `TBD`；README 总表 + 目录树 + 卡头部三处同步。

## 8. 验收清单（AC）🟨

> 判据设计原则：本里程碑的失败模式是 **「假驱动」** —— 消息被收到了但没起 run、
> run 起了但回调定位到了**另一个** run、按钮点了但 resume 的是一个**已终态**的 run。
> 这些**都不报错**。所以判据必须是**可数的事实**（起了几个 run / 是哪个 run / 什么状态）+ **负向用例**。

| # | 验收项 | 判据 | 验证方式 · 证据位置 |
|---|---|---|---|
| AC-1 | 群里一句话起 dev run | 日志出现新 `runId`，且其 `repo:target` 事件 `repoKey` === 消息里指定的仓库 | 脚本注入假事件 + 查日志（依赖 M6 的 runId 贯穿）；证据 `logs/m7-verify.log` |
| AC-2 | **路由安全（负向）** | 无仓库标识 / 未知仓库 / 语法残缺 → **拒答 + 零 run 起**（`triggered.length === 0`，可数） | 单测 4 条负向用例 + 脚本断言；**核心判据** |
| AC-3 | **按钮回调真 resume** | 点「合并」→ 该 run 到终态且 `merged:true`（GitHub 侧可查）；点「拒绝」→ `merged:false` 且 PR **仍 open** | 真飞书群人工操作 + REST 查 PR 状态 |
| AC-4 | **回调定位到正确的 run** | 同群存在 A、B 两个 run 时，点 A 卡片的按钮 → **只有 A 被 resume**（B 状态不变） | 脚本构造双 run 场景；**核心判据**（防「假驱动」） |
| AC-5 | **回调标识结构化且可追溯** | 卡片 value 是 **JSON 对象**且含 `kind` / `action` / `runId`（dev 另含 `repoKey`）；`action` ∈ 闭集；**全程无任何拼接分隔符**；该 runId 能在日志里查到完整时间线（**依赖 M6 AC-5**） | 脚本解析卡片 JSON（断言字段集与闭集）+ 查日志 |
| AC-6 | 重投幂等 | 同一条消息投 2 次 → `triggered.length === 1`，`skipped` 含 1 条 `duplicate` | 脚本断言（复用 M5a 去重表） |
| AC-7 | 重启不重放 | 进程重启后再触发一轮 → **不起历史消息的 run**（游标生效） | 脚本：写游标 → 重启 → 再 poll |
| AC-8 | 准入控制（负向） | 白名单外身份触发 → 零 run + 审计事件存在 | 脚本注入非白名单 sender |
| AC-9 | 卡片信息完整 | 多仓库下卡片含**仓库名 + base 分支 + runId + PR 链接** | 人工看卡片 + 脚本断言卡片 JSON 字段 |
| AC-10 | 长连接韧性 | 主动断连 → 自动重连；重连期间的消息由游标补拉不丢 | 脚本杀连接 / 人工断网 |
| AC-11 | 旧能力不退化 | `insight-workflow` 仍可独立触发（分流不破坏它）；M5a 去重表语义不变 | 既有验证模式全绿 |
| AC-12 | 零回归 | 单测 ≥ 基线 + M4/M5/M6 全部验证模式绿 | 全量跑；证据 `logs/m7-verify.log` |
| AC-13 | pr-agent 工作树未被触碰 | 运行前后 `git status --short` 一致、无新增本地分支 | 脚本快照对比（同 M3/M4/M5/M6） |

> **AC-2 / AC-4 / AC-8 是本里程碑的核心价值**：它们验证的不是「功能多了」，
> 而是「**错误的路由被挡住了**」「**回调没有点错 run**」「**不该触发的人触发不了**」。
> 这三件事的失败模式都是**静默错误**（在错误仓库开了 PR / resume 了错误的 run / 无权限的人驱动了 agent）。

## 10. 异常与兜底 🟨

| 已知异常 | 判定条件（可执行） | 降级行为 | 是否阻断 AC |
|---|---|---|---|
| 长连接断开 | WS `close` / 心跳超时 | 指数退避重连；断开期间事件由**游标补拉**（不丢）；每次断连落一条事件 | 否（AC-10 专验） |
| 回调签名 / 鉴权校验失败 | signature 不匹配 或 app_id 不符 | **拒绝处理** + 落审计事件（防伪造触发） | **是**（安全属性） |
| 自然语言解析不出仓库 | 无显式仓库标识 | **拒答** + 回卡片列出可用仓库；零 run 起 | **是**（AC-2 的正面判据） |
| 指定了未知仓库 | `repoKey` 不在注册表 | 同上，**绝不回退到默认仓库** | **是**（AC-2） |
| 触发者不在白名单 | sender_id 未匹配 | 拒答 + 审计事件；零 run 起 | **是**（AC-8） |
| 回调到达时 run 已终态 | `resume` 报非 suspended | 回卡片「该 run 已结束（状态：X）」，**不重复执行** | 否 |
| 回调的 runId 在库里不存在 | `createRun({ runId })` 后 resume 失败 | 回卡片「找不到该 run」；落事件 | 否 |
| **回调 value 不合法**（非 JSON 对象 / 缺 `kind`·`action`·`runId`） | schema 校验失败 | **拒绝处理** + 落审计事件；不构造任何 resume | **是**（安全属性） |
| **未知 `action`**（不在闭集内） | 枚举校验失败 | **拒绝处理** + 落事件。⚠️ **禁止 `else` 兜底**（否则未知动作会静默走默认分支） | **是**（安全属性） |
| 回调的 `repoKey` 与卡片所属仓库不符 | 交叉校验失败 | 拒绝处理 + 落事件（防跨仓库误驱动） | **是**（安全属性） |
| 缺 `im:message.group_msg` 权限 | 收到 `code=230027` | 降级为「仅发不收」（M1 既有行为）；卡片**明示**该限制 | **是**（阻断 AC-1，但可单独验收「发」的部分） |
| 群开启保密模式 | `code=231203` | 同上，明确提示原因 | 否 |
| 同一群同一仓库并发触发 | 两个 run 争锁 | **串行执行**（M5 锁）；后到者等锁，日志可见 `repo:lock waitedMs` | 否 |

### 2026-09-17 · 拍板「回调 value 结构化」（只读核查，零代码改动）

**触发**：用户提议把回调标识的分隔符从 `_` 换成 `:`（理由：冒号在分词查询上优于下划线）。
核查后**接受其判断、但给出更优解**；用户拍板 **结构化**。

1. ✅ **飞书侧无任何障碍**（一手来源：官方「按钮(button)」组件文档 + 「配置卡片交互」）：
   原文「`value` 仅支持 key-value 形式的 JSON 结构，且 key 为 String 类型」，回调 `action.value`
   原样回传该对象。`callback_id` 是**项目自造的 key**（`feishu.ts:120`），不是飞书保留字段。
2. 🔑 **比换分隔符更优：取消拼接。** `merge_<n>` 把「哪个 run（身份）」与「哪个动作（意图）」压进一个字符串
   —— 与 M6 侦察出的 `stageStart('merge','rejected')` **同构**
   （两段语义塞进同一个 `string` 形参，编译器拦不住）。
   **通用判据**：只要两段语义的**消费方式不同**（一个用于定位、一个用于分支），就不该编进同一字符串；
   **修法也应复用**（M6 已定：改对象参数让误用无法编译）。
3. ⛔ **若坚持字符串，冒号有一条硬否决**：`:` 是 **Windows 文件名保留字符**
   （NTFS `\ / : * ? " < > |`，且兼作盘符分隔）。当前 per-run 日志文件名只用 `<runId>`（不含 action）
   → **碰巧没撞上，不是不会撞上**；若选 `:` 必须同时写明文约束「此标识不得用于文件名」。
   *（另两条支持冒号的理由成立：`_` 属 `\w`，`grep -w` / ripgrep `-w` / ES standard analyzer /
   编辑器全词匹配都当**一个 token**；且项目已有 `test:run` / `llm:done` / `repo:lock` 这类冒号事件名。
   但**结构化把这个问题整个消掉了**，所以不必在分隔符上做取舍。）*
4. ⚠️ **更正一处假约束**：见事实 4b。
5. ✅ **迁移窗口已测量**：见事实 4c → 现在改只需 2 个产出点 + 文档。
