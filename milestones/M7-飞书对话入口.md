## 0. 角色与责任 🟦

| 角色 | 是谁 | 在本里程碑做什么 / 何时介入 |
|---|---|---|
| 对话方 | **飞书群里的成员 / 私聊用户** | @bot 说一句话（带或不带指令）→ 得到 LLM 回答。机器人成为项目的**主入口**，取代 curl 与验证脚本 |
| 触发方 | 同上 | 本里程碑**只读**：任何指令都不写仓库、不起 workflow run |
| 验收方 | 开发者本人 | ① 在真实飞书群里走一遍（`/ask`、默认对话、`/help`、未知指令拒答）；② 跑验证脚本验边界（路由负向 / 幂等 / 未实现指令零副作用）。⚠️ **脚本能证明的极限是「路由与回执正确」，不能证明「群里真的收到了」** —— 后者必须人工看一眼 |
| 卡 Owner | 当前开发会话 | 推进 + 更新本卡 + 三处同步 |

> ⚠️ **本里程碑的安全性质已显著降低**（因为它不写仓库、不起 run）：
> 最坏情况是「回了不该回的话」，而不是「在真实仓库开了 PR」。
> 但仍保留最小策略（§3 M7-8），因为**默认意图 = 对话**意味着**任何人 @bot 都能消耗 LLM 额度**。

## 2. 为什么现在做（排序理由）🟦

| 理由 | 说明 |
|---|---|
| **Channel 是所有后续能力的共同地基** | 无论将来接 dev、insight、status 还是 cost，都要先有「常驻长连接 + 归一化消息 + 路由」。本卡把它单独做稳，M8 往上加 handler 时**不动框架** |
| **它是「项目真实目标」的第一块** | 用户 2026-09-16 的表态是「要能通过飞书直接控制这个项目」；2026-09-17 补充「也该支持正常与 LLM 交互」。**后者不需要等 M6 的任何东西** —— 可以立即交付 |
| **与 workflow 完全解耦，风险面最小** | 本卡不写仓库、不起 run、不碰闸门。失败模式是「没回话」而不是「开错 PR」。**先做低风险的一次，验证长连接在本机家庭网络下的真实稳定性** |
| **把外部未知一次性暴露** | 长连接是否真能同时收消息与卡片回调 / 是否受本机网络影响 / 官方 SDK 的 Channel 是否真如文档所述 —— 这些**只能实测**。放在最小切片里试错成本最低 |
| **M6 的成果在此处第一次被用户直接感知** | M6 建立了「可信 runId + 统一日志」。本卡复用同一套 logger 记录路由决策（`im:route`），使「消息到底路由对没有」可事后查 —— 这是判据可数的前提 |

> 📌 **与 M8 的顺序**：M7（本卡）→ M8。
> ⚠️ **原卡「M6 → M7 硬依赖」的表述已更正为「M6 → M8」**：
> 该论证的依据是「按钮回调要用标识定位 run」，而**按钮回调属 M8**；
> M7 只做对话，不依赖 `runId` 贯穿，**可以立即开工**。

## 3. 范围 / 明确不做 🟦

### 已核实的技术前提（一手来源，2026-09-17）

| # | 事实 | 证据 |
|---|---|---|
| 1 | **官方 SDK 有 `Channel` 高层模块**，专为对话式 bot 设计 | `@larksuiteoapi/node-sdk` 的 `docs/channel.md`：「`Channel` is a high-level module built on top of `WSClient`/`EventDispatcher`/`Client`. It bundles the chores of running a Feishu bot — transport, message normalization, **safety policy**, outbound sending, **streaming replies**, media upload, card interactions」 |
| 2 | **`createLarkChannel` API 形态** | `createLarkChannel({ appId, appSecret, policy, safety, outbound })` → `channel.on('message'\|'cardAction'\|'reject'\|'reconnecting'\|'reconnected')` → `await channel.connect()`；连接成功后 `channel.botIdentity` 可用 |
| 3 | **长连接同时支持消息与卡片回调** | `transport` 默认 `'websocket'`；`channel.on('cardAction')` 在 websocket 模式下可用。官方 Node 示例即以 `WSClient` + `EventDispatcher` 注册 `card.action.trigger` → **原 §0.1「长连接是否支持卡片回调」的疑问在此消解，不需要内网穿透** |
| 4 | **消息已归一化，无需手解析飞书结构** | `NormalizedMessage`：text / post / image / file / audio / video / sticker / merge_forward 等统一成 markdown + XML 标签；含 `chatId`/`chatType`/`senderId`/`content`/`mentions`/`mentionedBot`/`replyToMessageId` |
| 5 | **有原生流式回复** | `channel.stream(chatId, { markdown: async s => { ... await s.append(chunk) } }, { replyTo })`；先发 `"Thinking..."` 占位卡，服务端渲染打字机 |
| 6 | **SDK 自带策略层** | `policy: { requireMention, dmMode, groupAllowlist, dmAllowlist, respondToMentionAll }`；被策略拒绝时触发 `channel.on('reject')`，`RejectReason` ∈ `group_not_allowed` / `sender_not_allowed` / `no_mention` / `dm_disabled` / `mention_all_blocked` |
| 7 | **SDK 自带 safety 层** | dedup window / stale threshold / **per-chat 串行** / 批量合并。⚠️ 注意 dedup 是**内存**级（见下「三层幂等」） |
| 8 | **长连接只能收、不能发** | 官方 Python 文档明示「ws.Client 只能用来接收事件」；Node 侧 `Channel` 已把发送封装好（底层走 `Client`），无需自己区分 |
| 9 | **社区标准做法一致** | OpenClaw / Hermes / Qwen Code 均为「自建应用 + WebSocket 长连接 + 订阅 `im.message.receive_v1`」；Qwen Code 源码直接使用 `@larksuiteoapi/node-sdk` 的 `WSClient` |

### 三层幂等的分工（必须写清，否则会被当成重复建设）

| 层 | 位置 | 挡什么 | 生效范围 |
|---|---|---|---|
| 1 | SDK `safety` dedup | 长连接的**秒级重投** | **内存**，进程重启即失效 |
| 2 | SDK `safety` per-chat 串行 | 同一会话的并发处理 | 内存 |
| 3 | M5a `dedup-store`（SQLite 唯一索引 + 游标） | **跨重启**的重复触发 | **持久化** |

> 本卡三层全用：层 1/2 由 SDK 提供（零成本），层 3 复用 M5a 既有实现（`source = feishu:<chatId>`）。
> ⚠️ **不要因为「SDK 已有 dedup」就删掉层 3** —— SDK 那层重启就没了。

### 做

- **M7-1 Channel 常驻接入**
  用 `createLarkChannel` 建立长连接，注册 `message` / `cardAction` / `reject` / `reconnecting` / `reconnected` / `error` 六类事件。
  ⚠️ **`cardAction` 本卡只注册、不消费**（M8 才用）—— 注册它是为了**在本卡就实测「长连接能收到按钮回调」**，
  把这条外部未知提前证伪，避免 M8 做到一半发现要走内网穿透。
  常驻化：优雅退出（`SIGINT` → `channel.disconnect()`）、重连事件落日志。
- **M7-2 指令路由表 + 解析器（本卡第一交付物）**
  - **路由表是契约，先定全**（§7 给出完整表：7 条指令 + 默认意图）；本卡**只实现 `/ask` 与 `/help`**。
  - 解析器为**纯函数**（无 IO、无 LLM），入参 `{ text, chatType, mentionedBot }`，出参
    `{ command, repoKey?, arg, decision: 'dispatch' | 'reject', reason? }`。
  - **禁止 `else` 兜底**：未知指令必须显式拒绝，不得静默走默认分支。
  - 每次决策落一条 `im:route` 事件（复用 M6 统一 logger），使「路由对不对」可事后查。
- **M7-3 `/ask` 通用 LLM 对话（含流式）**
  新增 `src/mastra/agents/ask-agent.ts`（Mastra `Agent`，与 `dev-agent`/`insight-agent` 同族），
  经 `channel.stream()` 输出。**无状态单轮**（已拍板）。
- **M7-4 `/help` 指令清单卡片** ——列出全部指令 + 每条状态（可用 / 规划中），使人无需读文档即可上手。
- **M7-5 默认意图 = 对话** —— 无 `/` 前缀的消息固定走 `/ask`。
  ⚠️ **这是确定性规则，不是「LLM 猜意图」**：不猜流程，只把「没写指令」解释为「要用默认指令」。
- **M7-6 未实现指令的明确回执** —— `/dev`、`/insight` 等在本卡**被识别但不执行**，
  回「该指令将在 M8 接入」，**零 run 起、零副作用**。
- **M7-7 3 秒内 ACK + 异步执行** —— 长连接要求事件处理器快速返回（超时会触发重推）。
  收到消息后**先回执/占位，再异步跑 LLM**。
- **M7-8 最小策略** —— `policy: { requireMention: true }` + 订阅 `reject` 落审计事件。
  自研人级白名单**不做**（用户 2026-09-17：「权限之类的先不考虑」）。
- **M7-9 验证脚本 + 单测 + AC 回填 + 三处文档同步**

### 明确不做（每条都指明去向，不留无主债务）

| 不做的事 | 去向 |
|---|---|
| ❌ `/dev` 分流到 `dev-workflow`（一句话 → issueNumber/issueTitle/issueBody/target 的映射） | **→ M8**（含「是否先建真 issue」的待拍板项） |
| ❌ `/insight` 分流到 `insight-workflow` | **→ M8** |
| ❌ 卡片按钮回调 → `resume` | **→ M8**（本卡只注册 `cardAction` 事件以实测连通性） |
| ❌ 卡片 V1 → **V2 schema 迁移**（按钮回调的硬前提，见 M8 §3） | **→ M8** |
| ❌ 卡片补 `target` / `runId` | **→ M8** |
| ❌ 自研准入白名单（`FEISHU_ALLOWED_USERS`） | **→ M8**（本卡用 SDK `policy` 兜最小策略） |
| ❌ 会话持久化 / 多轮记忆 | **→ 更后续**（本卡已拍板「无状态单轮」） |
| ❌ `/status`、`/cost` | **→ M8**（见 §0.1 待拍板项 1） |
| ❌ 多群 / 多租户隔离 | 单实例单群够用；多群会让白名单变成二维矩阵 |
| ❌ 卡片上的自由文本多轮交互 | 只做确定性指令；自由文本对话走 `/ask` 独立通路 |
| ❌ 内网穿透 / Webhook 模式 | 长连接已满足；webhook 需公网入口与签名校验，本机不具备条件 |
| ❌ 改闸门判据归属 / 改八步拓扑 / 改 M5 幂等与锁 | 本卡不碰 workflow 层 |

## 4. 端到端演示效果 🟦

**在飞书群里（或私聊）：**

```
@bot /ask 这个项目现在支持哪些工作流？
```

**看到：**

1. 卡片先出现 `Thinking...` 占位
2. 同一张卡片**流式**输出回答（打字机效果，服务端渲染）
3. 回复挂在原消息下（`replyTo`），群里上下文不散

**六条可复现的演示路径：**

| 路径 | 输入 | 预期 |
|---|---|---|
| A 指令对话 | `/ask 这个项目支持哪些工作流？` | 流式回答；日志 `im:route` 记 `command=ask, decision=dispatch` |
| B **默认意图** | `@bot 你好，介绍一下你自己`（**无指令**） | 同样得到流式回答；日志 `reason=default` |
| C **未知指令拒答** | `/foo 随便什么` | 回「未知指令，可用：…」；**零 LLM 调用、零 run** |
| D **未实现指令不静默** | `/dev [repo-A] 给 README 加一节` | 回「该指令将在 M8 接入」；**零 run 起**（不是静默失败，也不是偷偷起 run） |
| E 未知仓库拒答 | `/dev [no-such-repo] xxx` | 回「未知仓库，可用：repo-A / repo-B」；**绝不回退默认仓库** |
| F 重投幂等 | 长连接把同一条消息重投 3 次 | 只回 1 次；日志可见 2 条 dedup 丢弃 |

| 模块 | 导入路径 | 职责 | 为什么用它，而不是裸写 |
|---|---|---|---|
| **`createLarkChannel`** | `@larksuiteoapi/node-sdk` | 常驻长连接 + 消息归一化 + 策略 + 发送 + 流式 | 官方高层抽象，把「跑一个飞书 bot 的杂活」全包了。**本卡的选型核心** |
| `channel.on('message')` | 同上 | 收消息 | 直接拿 `NormalizedMessage`，**不必解析飞书的 10 余种 `msg_type`** |
| `channel.on('cardAction')` | 同上 | 收按钮回调 | 本卡**只注册不消费**，用于实测长连接支持性 |
| `channel.stream()` | 同上 | 流式回复 | 原生打字机，**不必手写 `updateCard` 轮询**（手写会有节流、限流、并发覆盖三个坑） |
| `channel.send()` | 同上 | 发文本 / 卡片 | 自带 `replyTo` / `replyInThread` / 结构化 `mentions`，以及两类自动降级（回复目标被撤回、post 结构被拒） |
| `channel.updateCard()` | 同上 | 原地更新卡片 | `/help` 与将来的 dev 卡片都用它 |
| `channel.rawClient` | 同上 | 逃生舱 | 需要直调 Open API 时不必再建 client |
| `Agent` | `@mastra/core` | `/ask` 的对话 | 与 `dev-agent`/`insight-agent` 同族，沿用既有 LLM provider 抽象（`llm/providers.ts`），**不裸调 LLM** |

**选型备注：**

1. **为什么从 `WSClient` 上移到 `Channel`**：原卡（现 M8）选定的是低层 `WSClient` —— 那需要自己解析消息、自己拼卡片、
   自己做不了流式。`Channel` 把这一层全包了，且**同时支持消息与卡片回调**（原卡 §0.1 第 1 条的未知项随之消解）。
   代价是新增一个依赖 `@larksuiteoapi/node-sdk`（**不可避免** —— 自写 WebSocket 要实现握手/心跳/重连/签名，不划算且更不可靠）。
2. **`Channel` vs `WSClient` 的取舍线**（官方原话）：需要对话式 bot 能力（流式、卡片交互、媒体、@ 策略）→ 用 `Channel`；
   只需收几个事件做简单处理 → `WSClient` 就够。**本项目属前者。**
3. **不用内网穿透**：`ngrok` / `frp` 会引入外部依赖 + 一个公开暴露的端点，而长连接不需要公网入口。
4. **路由解析不用 LLM**：见 §3 M7-5 与 M8 §3 M7-2 的不对称代价论证 —— 流程错会走错 handler，代价不对称。

  | 指令 | 语法 | 仓库 | 本卡状态 | 去向 |

  | `/ask` | `/ask [<repo>] <问题>` | 可选 | ✅ **实现** | `ask-agent` 通用对话 |
  | `/help` | `/help` | — | ✅ **实现** | 回指令清单卡片 |
  | （无指令） | `<任意文本>` | — | ✅ **实现** | 默认 → `/ask` |
  | `/dev` | `/dev [<repo>] <需求>` | **必填** | 🟨 识别但拒绝执行 | M8 → `dev-workflow` |
  | `/insight` | `/insight [<repo>] <问题 \| #issue>` | **必填** | 🟨 识别但拒绝执行 | M8 → `insight-workflow` |
  | `/status` | `/status [#<runId>]` | — | 🟨 识别但拒绝执行 | M8 → M6 日志时间线 |
  | `/cost` | `/cost [<repo>]` | 可选 | 🟨 识别但拒绝执行 | M8 → M6 成本归口 |

  **解析规则（确定性，不含 LLM）**：
  1. 以 `/` 开头 → 取首段为指令名 → 查**闭集**。命中 → 走对应 handler；未命中 → **拒绝**（不猜、不兜底）。

  3. 无 `/` 前缀 → 默认意图 `/ask`（`reason='default'`，可观测）。
- 验收：**单测 ≥ 12 条**，含 **5 条负向**（未知指令 / 未知仓库 / 仓库语法残缺 `[` 不成对 / 只发 `/` / 只 @bot 不说话），
  断言「**返回 reject 且 reason 明确，绝不 dispatch、绝不返回默认仓库**」。

## 8. 验收清单（AC）🟨

> 判据设计原则：本里程碑的失败模式是 **「接错端口」** ——
> 消息收到了但路由到错的 handler、指令没实现却静默无回、长连接断了没人知道。
> 这些**都不报错**（群里只是"没人理你"）。所以判据必须是**可数的事实**（路由决策数 / 回执数 / 零 LLM 调用）+ **负向用例**。

| # | 验收项 | 判据 | 验证方式 · 证据位置 |
|---|---|---|---|
| AC-1 | 长连接连通且可重连 | `connect()` resolve 且 `channel.botIdentity` 非空；断连后自动重连（`reconnecting` + `reconnected` 事件各 ≥1） | 脚本 + 人工断网；`logs/m7-verify.log` |
| AC-2 | **`/ask` 流式对话可用** | 真群里 `/ask <问题>` → 卡片流式输出完整回答，且挂在原消息下 | **真飞书群人工**（脚本无法证明"群里真收到了"） |
| AC-3 | **默认意图 = 对话** | 无 `/` 前缀的消息 → 日志 `im:route` 的 `command='ask'` 且 `reason='default'` | 脚本注入假事件 + 查日志 |
| AC-4 | `/help` 返回指令清单 | 卡片含全部 7 条指令，且**状态标注与实际一致**（未实现的不得标为可用） | 脚本解析卡片 JSON 断言 |
| AC-5 | **路由拒绝零副作用** | 未知指令 `/foo`、未知仓库 `[no-such-repo]`、语法残缺 → 回拒绝提示，**零 run 起、零 LLM 调用**（`triggered.length === 0`，可数） | 单测 5 条负向 + 脚本断言；**核心判据** |
| AC-6 | **未实现指令不静默** | `/dev`/`/insight`/`/status`/`/cost` → 明确回执「M8 接入」+ **零 run 起** | 脚本断言（**核心判据**：失败模式是"偷偷起了 run"或"什么都不回"） |
| AC-7 | 仓库白名单生效 | 未知 `repoKey` → 拒绝，且**绝不回退到默认仓库**（断言返回值里没有 fallback 仓库名） | 单测 + 脚本 |
| AC-8 | 重投幂等 | 同 `messageId` 投 3 次 → 只处理 1 次，其余记为 dedup 丢弃 | 脚本断言 |
| AC-9 | 3 秒内 ACK | 从收到事件到首次可见回执 ≤ 3s（长连接超时要求） | 脚本测时 |
| AC-10 | 策略拒绝可观测 | 未 @bot 的群消息 → 不触发对话，且 `im:reject` 事件含 `RejectReason` | 脚本注入 + 查日志 |
| AC-11 | 旧能力不退化 | `insight-workflow` 仍可独立触发；M4/M5/M6 全部验证模式绿 | 全量跑 |
| AC-12 | 零回归 | 单测 ≥ 基线（M6 收口时 **291**） | 全量跑；`logs/m7-verify.log` |
| AC-13 | pr-agent 工作树未被触碰 | 运行前后 `git status --short` 一致、无新增本地分支 | 脚本快照对比（同 M3/M4/M5/M6） |

> **AC-5 / AC-6 / AC-7 是本里程碑的核心价值**：它们验证的不是「功能多了」，
> 而是「**未知的东西没有被猜**」「**没实现的没有假装实现**」「**没指定的仓库没有被默认**」。
> 三条的失败模式都是**静默错误**，在群里表现为「机器人没反应」或「回答了但答错了对象」。

## 10. 异常与兜底 🟨

| 已知异常 | 判定条件（可执行） | 降级行为 | 是否阻断 AC |
|---|---|---|---|
| 长连接断开 | WS `close` / 心跳超时 | SDK 自动重连（`autoReconnect`）；`reconnecting`/`reconnected` 落日志 | 否（AC-1 专验） |
| `connect()` 失败 | 15 秒握手超时 → `LarkChannelError(code='not_connected')` | 进程退出并**明确报错**（不静默空转）；区分 `permission_denied`（凭据/权限问题）与 `not_connected`（网络问题） | **是** |
| 未 @bot 的群消息 | `policy.requireMention` 拦截 | 触发 `on('reject', 'no_mention')` → 落事件、**不回复**（避免群里噪音） | 否（AC-10） |
| LLM 调用失败 / 超时 | `ask-agent` 抛错 | 卡片追加 `"— (生成中断)"`（`channel.stream` 内建行为）+ 落事件；**不静默留一张空卡** | 否 |
| 消息类型不支持 | `NormalizedMessage.rawContentType` 非 text/post | 仍走归一化后的 `content`（Channel 已处理）；若 `content` 为空 → 回提示「暂不支持该消息类型」 | 否 |
| 路由解析失败 | 未知指令 / 未知仓库 / 语法残缺 | **拒绝 + 回提示**（列出可用指令或可用仓库）；零 LLM 调用 | **是**（AC-5/AC-7） |
| 指令已识别但未实现 | `/dev` `/insight` `/status` `/cost` | 回「该指令将在 M8 接入」；**零 run 起** | **是**（AC-6） |
| 长连接**不支持**卡片回调 | 本卡实测发现 | 记录事实 → **M8 需重议选型**（内网穿透 + Webhook）；⚠️ 这是本卡要提前证伪的最大外部未知 | 否（但影响 M8） |
| SDK `safety` dedup 与 M5a dedup 冲突 | 重复回执 / 误丢 | 两层键不同（SDK 用事件 id，M5a 用 `messageId`）；若实测冲突 → **以 M5a 为准**，SDK 层关掉 | 否 |
| 飞书权限不足 | `code=230027`（缺 `im:message.group_msg`） | 群消息收不到 → 降级为「仅私聊 + 仅发不收」；卡片/日志**明示**该限制 | 否（私聊路径可独立验收） |
| 机器人被移出群聊 | `im.chat.member.bot.deleted_v1` | 落事件；不重试（避免刷屏） | 否 |
| 同一会话并发消息 | SDK per-chat 串行 | 串行处理；后到者等待 | 否 |
