## 0. 角色与责任 🟦

| 角色 | 是谁 | 在本里程碑做什么 / 何时介入 |
|---|---|---|
| 触发方 | **飞书群里的成员** | 在群里 `@bot /dev [<repo>] <需求>` —— **仓库标识必须显式**（见 §3 缺口 3）。机器人取代 curl / 验证脚本成为主入口 |
| 审批方 | **群内的人，点卡片按钮** | 卡片上的「🔀 合并 / ❌ 拒绝」按钮 → `card.action.trigger` 回调 → resume。**这是本里程碑的核心交付**，取代现在的「手工打 HTTP resume 端点」 |
| 验收方 | 开发者本人 | ① 在真实飞书群里走一遍完整链路；② 跑验证脚本验边界（路由 / 回调隔离 / 重投 / 并发）。**脚本能证明的极限是「回调被正确处理」，不能证明「群里真的收到了」** —— 后者必须人工看一眼 |
| 卡 Owner | 当前开发会话 | 推进 + 更新本卡 + 三处同步 |

> ⚠️ **准入是安全边界，不是可选项**：一旦群里的人能让 agent 在真实仓库上跑代码并开 PR，
> 「谁有资格触发」就必须显式定义（§0.1 待拍板项 2）。
> 📌 **M7 的默认意图 = 对话已使「任何人 @bot 都能消耗 LLM 额度」成立**，本卡把它升级为
> 「任何人 @bot 都能在真实仓库跑代码并开 PR」—— **风险等级完全不同**，所以自研白名单在本卡必须做。

### 0.1 开工前待拍板（2 条）

> 📌 **为什么放在 §0**：这些是**建卡期就产生的决策项**，全卡 + `README.md` 多处写作「§0 待拍板项 N」。

1. **业务标识与 issue 的关系**：群里一句话要不要**先在 GitHub 建一个真 issue**（拿到真 `issueNumber`，
   代价是多一次写操作）？还是**不建 issue**（用 `runId` 当业务标识）？
   还是**要求消息里自带 issue 号**（`/dev [repo-A] #12 修 xxx`，最省事但要求人先建 issue）？
   → 这决定了 M8-1 的映射实现与卡片的可读性。
   📌 **倾向「不建真 issue」**：`/dev` 的入参是自由文本，而 `ContextSchema` 要求
   `issueNumber`/`issueTitle`/`issueBody`（`dev-workflow.ts:168-222`）。
   最省事的做法是**从消息派生**（`issueTitle` = 首行摘要、`issueBody` = 全文、
   `issueNumber` 用 `runId` 派生的稳定数字或改为可选）。**但改 `ContextSchema` 会动编排层契约**，
   所以这条必须先拍板再动手。
2. **准入控制**：谁能触发？候选：① 群成员皆可 ② `FEISHU_ALLOWED_USERS` 白名单（user_id 列表）
   ③ 群成员 + 白名单双层。
   ⚠️ **默认绝不能是 ①** —— 它意味着群里任何人可让 agent 在真实仓库跑代码并开 PR。
   📌 M7 已用 SDK `policy`（`requireMention` / `allowlist`）兜住「群级」策略；
   本卡要补的是**人级**（`sender_not_allowed` 之上的细分），因为 SDK 的 allowlist 粒度不覆盖「同一群里区分谁」。

## 2. 为什么现在做（排序理由）🟦

| 理由 | 说明 |
|---|---|
| **这才是这个项目的产品形态** | M1–M6 一直是在「把链路做对」（只读 → 本地写 → 真 PR → 真闸门 → 多仓库 → 可观测），M7 做了「住进飞书」。**但「能通过飞书控制这个项目」才是用户的真实目标**（2026-09-16 原话），本卡收口这最后一段 |
| **无主债务到期（见卷首 A）** | 按钮回调被四处承诺、无人承接。**不主动立项，它会继续漂** |
| **前置已被 M6 解掉** | 按钮回调的本质是「**用一个标识定位挂起的 run 并 resume**」。M6 之后卡片才能携带可信 `runId`（原状：日志 `runId` 覆盖率 **0/701**，唯 6 条是 `'rejected'`/`'resumed'` 污染值） |
| **前置已被 M7 解掉** | Channel 常驻、消息归一化、指令路由、`cardAction` 事件注册、3 秒 ACK、幂等第 3 层 —— **全部就位且不动框架** |
| **「多人从群里触发」的两个必然问题已被 M5 提前修** | ① **重复触发** → 入口幂等（唯一索引原子认领 + 游标）；② **同仓库并发导致提交落错分支** → 每仓库串行锁。**M5 的立项理由里写的就是这个场景** |
| **⚠️ 不做的话，剩下的能力全是「半自动化」** | 现在每一步都要人手工喂入参、手工 resume。工具做了七轮，仍然不是「能用的东西」 |

### 排序论证：为什么 M6 在 M8 之前（而不是「飞书最想要所以最先做」）

> 这是本卡最容易被反复追问的一条 —— 因为「**通过飞书控制这个项目**」是用户的真实目标，
> 直觉上「最想要的该最先做」。但顺序不由「谁重要」决定，由**谁阻塞谁**决定。

| # | 论证 | 事实底座 |
|---|---|---|
| 1 | **回调能力的前提是「可信标识」，而标识在 M6 之前不可信** | 回调 = `resume(runId)`。M6 前：日志 `runId` 覆盖率 **0/701**；卡片标识是 `merge_<issueNumber>`（多仓库下必然撞号） |
| 2 | **先做飞书会得到「能跑但不能验收」的里程碑** | 本卡**核心判据 AC-4**（回调定位到正确的 run、只有 A 被 resume）只能靠「构造双 run + **查日志确认**」来验 → **没有 runId 贯穿，这条判据根本执行不了**。能点通按钮 ≠ 验得出来点对了 |
| 3 | **依赖单向，顺序没有选择余地** | M6 的全部工作作用在**既有链路**上；M8 依赖 M6 的产物。反向做就得造临时标识来验回调，验完再拆掉 |
| 4 | **先做飞书 = 返工** | 卡片 value 会先做成 `merge_<issueNumber>`，M6 做完还得回头改卡片。M6 先做则一次做对 |
| 5 | **两者验收方式不同，合并会无法统一收口** | M6 判据**全部可程序判**（可数）；M8 判据需**真人 + 真群 + 真网络**（真按钮真 merge）。并成一张卡 → 「一半靠脚本、一半靠人在群里点」，给不出单一通过标准 |
| 6 | **外部未知不该污染确定性** | M6 新增外部依赖 = **零**。而飞书侧有未实测项（原为「长连接是否支持 `card.action.trigger`」——**该项已在 M7 立项时实测消解**；剩 `im:message.group_msg` 权限 M1 实测**是缺的**，`code=230027`） |

> 📌 **「立项」与「开工」是两件事。** 本卡的前身（原 M7）2026-09-16 就建了，
> 建卡是为了**把 6 处悬空承诺定性、把范围锁死**（`README.md` 全局原则第 9 条「不做项不许悬空」），
> **不构成「插队」的理由**。**建卡防漂移，顺序按依赖。**
> 📌 **M6 也不是纯为 M8 铺路**：成本回写、失败重试告警、`repo:lock` 泄漏这类不对称的可观测，自身就是收益。

> ⚠️ **两条风险（本卡必须显式声明）**：
> 1. **并发压力上升**。群聊里多人同时 `/dev` → 同仓库 run 会**排队**（M5 串行锁）。
>    且 M5 已知 **`REPO_LOCK_TTL_MS`(30min) > `REPO_LOCK_WAIT_MS`(10min)** ——
>    一次异常退出会让该仓库**显式失败**而非等过去。现在这个窗口会**被真实撞上**（不再是理论值）。
>    → 本卡应把这两条从「已知残余风险」升格为**需要观测的量**（依赖 M6 的日志）。
> 2. **触发即执行 agent 写下的代码**。准入（M8-6）不是锦上添花 —— 它决定了「谁能让 agent 在真实仓库上跑代码并开 PR」。
>    📌 M7 的默认意图 = 对话已使「任何人 @bot 都能消耗 LLM 额度」成立；本卡让它变成「能在真实仓库开 PR」，
>    **风险等级完全不同**，所以自研白名单在本卡**必须做**（不能像 M7 那样只靠 SDK policy）。

## 6. 用到的 Mastra / SDK 模块（本里程碑重点）🟨

> 本节只写选型结论 + 取舍理由，源码行号归 §11。

|---|---|---|---|
| `channel.on('cardAction')` | `@larksuiteoapi/node-sdk` | **收按钮回调**（本卡核心） | M7 已注册该事件；本卡只是**开始消费**它。回调 value 原样回传，无需自己解析飞书卡片结构 |

| `run.resume({ approved })` | `@mastra/core/workflows` | 唤醒挂起的 run | 与 M3 的人工闸门**同一条路径**，只是触发方从「手工 HTTP」变成「飞书回调」—— 语义零变化，风险可控 |
| `LibSQLStore`（`mastra_workflow_snapshot`） | `@mastra/libsql` | 跨进程 resume 的持久化前提 | ⚠️ 必须配。不配 storage 时按 runId 重建再 resume 会报 `This workflow run was not suspended`（`mastra/index.ts:36-39` 已记录此坑） |
| `Workflow` / `createStep` | `@mastra/core/workflows` | 八步编排 | **不改拓扑**。本卡的改动全部落在**入口侧与回调侧** |

  官方 common issues 明确把「按钮不触发」归因于 V1 schema —— 这是本卡最容易低估的工作量。
- **不用内网穿透**：长连接已满足（M7 实证）。
- **路由解析不用「纯 LLM 自由解析」**：M7 已实现约束式路由，本卡直接消费。

## 7. 任务分解 🟨

### M8-1 入口分流到 `dev-workflow`（承接缺口 1、2）
- 内容：`/dev` handler → 把「一句话 + repoKey」映射成 `ContextSchema`；
  起 `dev-workflow`；`/insight` 保留为独立命令。
- 验收：群里一句话真起 `dev-workflow` run；日志出现该 runId 且 `repo:target` 事件里 `repoKey` 正确。
- ⚠️ 前置：§0.1 第 1 条（issue 关系）必须先拍板，因为它决定是否改 `ContextSchema`。

### M8-2 卡片 V1 → V2 迁移（承接缺口 8）
- 内容：`buildCard`（`feishu.ts:110-132`）与 `buildDevCompleteCard`（`:135-173`）迁 V2 schema。
- 验收：迁移后**按钮在真群里能被点中并触发回调**（这是 V2 迁移成功的唯一硬判据）。

### M8-3 卡片按钮回调 → resume（**2026-09-17 拍板：结构化 value，无分隔符**）

- **value 形态 —— 唯一权威定义，两处产出点必须与之一致**

  | 卡片 | value（JSON 对象） |
  |---|---|
  | dev（`adapters/feishu.ts:169-170`） | `{ kind: 'dev', action: 'merge' \| 'reject', runId, repoKey }` |
  | insight（`workflows/insight-workflow.ts:234`） | `{ kind: 'insight', action: 'confirm' \| 'rerun', runId }` |

  | 字段 | 为什么必须有 |
  |---|---|
  | `kind` | 两种卡片的回调**打到同一个接收端** → 必须能分流。旧方案靠前缀（`merge_` / `confirm_`）**隐式**承担了这个职责，结构化了就得**显式**写出来 |
  | `action` | 动作。⚠️ **必须过闭集校验**（zod enum）；未知 action → 拒绝 + 落事件。**禁止 `else` 兜底**（否则未知动作静默走默认分支 —— 与 M4「判据归属」要的严格性同一要求） |
  | `runId` | 定位 run。**`issueNumber` 从此彻底退出回调标识**（它只在单仓内唯一，M5 多仓库后必然撞号） |
  | `repoKey` | 多仓库下的**交叉校验**（防「B 的卡片被当成 A 的回调」）。**只写逻辑标识，本机 clone 路径绝不进卡片**（同 M5 铁律） |

- **飞书侧约束（一手来源已核）**：`value` **仅支持 key-value 形式的 JSON 结构，且 key 为 String 类型**
  → 结构化天然满足，**对字符串内容无字符集限制**。
  ⚠️ `docs/archive/11-IM驱动的多Agent自动开发工作流设计.md:125` 的「`callback_id` ≤128、
  仅字母数字下划线短横线」**查无一手来源，勿引用**（真正的上限是整张卡片的体积）。
- 处理流程：**schema 校验 → `createRun({ runId })` → `resume({ approved })`**；
  **run 已终态 / runId 不存在 / value 非法** 三种都要有明确回执（见 §10）。
- 迁移触点：`feishu.ts:169-170`、`insight-workflow.ts:234`。
  ✅ **迁移窗口已测量（2026-09-17）**：全仓**无任何解析器**（`split|match|slice|indexOf` 在三处相关文件零命中；
  `test/` 无断言按钮 value 的用例）→ 现在改只需 2 个产出点 + 1 个解析器。
  📌 **教训：约定类改动要抢在「第一个消费者」落地之前做** —— 本任务写完解析器后再改，就是
  「改代码 + 改测试 + 改已发出去的卡片」。
  ⚠️ **但本卡的迁移窗口比原计划窄了**：M7 的 `/help` 卡片会先按 V2 上线
  （虽不消费 `cardAction`，但卡片结构已 V2）→ 本卡迁移时**以 M7 的卡片实现为参照**，保持一致。
- 验收：点「合并」→ PR 真 merged（可查 GitHub）；点「拒绝」→ run 终态且 PR 仍 open。

### M8-4 卡片补 target / runId（承接缺口 4）

## 8. 验收清单（AC）🟨

> 判据设计原则：本里程碑的失败模式是 **「假驱动」** —— 消息被收到了但没起 run、
> run 起了但回调定位到了**另一个** run、按钮点了但 resume 的是一个**已终态**的 run。
> 这些**都不报错**。所以判据必须是**可数的事实**（起了几个 run / 是哪个 run / 什么状态）+ **负向用例**。

| # | 验收项 | 判据 | 验证方式 · 证据位置 |
|---|---|---|---|
| AC-1 | 群里一句话起 dev run | 日志出现新 `runId`，且其 `repo:target` 事件 `repoKey` === 消息里指定的仓库 | 脚本注入假事件 + 查日志（依赖 M6 的 runId 贯穿）；证据 `logs/m8-verify.log` |
| AC-2 | **路由安全（负向）** | 无仓库标识 / 未知仓库 / 语法残缺 → **拒答 + 零 run 起**（`triggered.length === 0`，可数） | 复用 M7 的单测 + 本卡脚本断言；**核心判据** |
| AC-3 | **按钮回调真 resume** | 点「合并」→ 该 run 到终态且 `merged:true`（GitHub 侧可查）；点「拒绝」→ `merged:false` 且 PR **仍 open** | 真飞书群人工操作 + REST 查 PR 状态 |
| AC-4 | **回调定位到正确的 run** | 同群存在 A、B 两个 run 时，点 A 卡片的按钮 → **只有 A 被 resume**（B 状态不变） | 脚本构造双 run 场景；**核心判据**（防「假驱动」） |
| AC-5 | **回调标识结构化且可追溯** | 卡片 value 是 **JSON 对象**且含 `kind` / `action` / `runId`（dev 另含 `repoKey`）；`action` ∈ 闭集；**全程无任何拼接分隔符**；该 runId 能在日志里查到完整时间线 | 脚本解析卡片 JSON（断言字段集与闭集）+ 查日志 |
| AC-6 | **卡片 V2 schema 生效** | 卡片 JSON 使用 V2 结构（`behaviors: [{type:'callback'}]`），且**真群点击能触发回调** | 脚本断言结构 + **人工点一次**（结构对了但点不动 = 没通过） |
| AC-7 | 重投幂等 | 同一条消息投 2 次 → `triggered.length === 1`，`skipped` 含 1 条 `duplicate` | 脚本断言（复用 M5a 去重表） |
| AC-8 | 重启不重放 | 进程重启后再触发一轮 → **不起历史消息的 run**（游标生效） | 脚本：写游标 → 重启 → 再触发 |
| AC-9 | 准入控制（负向） | 白名单外身份触发 → 零 run + 审计事件存在 | 脚本注入非白名单 sender |
| AC-10 | 卡片信息完整 | 多仓库下卡片含**仓库名 + base 分支 + runId + PR 链接** | 人工看卡片 + 脚本断言卡片 JSON 字段 |
| AC-11 | 旧能力不退化 | `insight-workflow` 仍可独立触发（分流不破坏它）；M5a 去重表语义不变；**M7 的 `/ask`、`/help`、默认意图仍可用** | 既有验证模式全绿 |
| AC-12 | 零回归 | 单测 ≥ 基线（M6 收口时 **291**，M7 完成后取新基线）+ M4/M5/M6/M7 全部验证模式绿 | 全量跑；证据 `logs/m8-verify.log` |
| AC-13 | pr-agent 工作树未被触碰 | 运行前后 `git status --short` 一致、无新增本地分支 | 脚本快照对比（同 M3/M4/M5/M6/M7） |

> **AC-2 / AC-4 / AC-6 / AC-9 是本里程碑的核心价值**：它们验证的不是「功能多了」，
> 而是「**错误的路由被挡住了**」「**回调没有点错 run**」「**卡片真的能点**」「**不该触发的人触发不了**」。
> 四件事的失败模式都是**静默错误**（在错误仓库开了 PR / resume 了错误的 run / 按钮是死的 / 无权限的人驱动了 agent）。

## 10. 异常与兜底 🟨

| 已知异常 | 判定条件（可执行） | 降级行为 | 是否阻断 AC |
|---|---|---|---|
| 回调签名 / 鉴权校验失败 | signature 不匹配 或 app_id 不符 | **拒绝处理** + 落审计事件（防伪造触发） | **是**（安全属性） |
| 指定了未知仓库 | `repoKey` 不在注册表 | **拒答** + 回卡片列出可用仓库；**绝不回退到默认仓库** | **是**（AC-2） |
| 触发者不在白名单 | sender_id 未匹配 | 拒答 + 审计事件；零 run 起 | **是**（AC-9） |

| 回调的 `repoKey` 与卡片所属仓库不符 | 交叉校验失败 | 拒绝处理 + 落事件（防跨仓库误驱动） | **是**（安全属性） |

| 缺 `im:message.group_msg` 权限 | 收到 `code=230027` | 降级为「仅私聊 + 仅发不收」（M1 既有行为）；卡片**明示**该限制 | **是**（阻断 AC-1，但可单独验收「发」的部分） |
| 群开启保密模式 | `code=231203` | 同上，明确提示原因 | 否 |
| 同一群同一仓库并发触发 | 两个 run 争锁 | **串行执行**（M5 锁）；后到者等锁，日志可见 `repo:lock waitedMs` | 否 |
| ⚠️ 锁 TTL 抢占窗口被真实撞上 | 前一个 run 异常退出（TTL 30min > WAIT 10min） | 该仓库后续 run **显式失败**（刻意：宁可显式失败也不静默双跑）；**由 M6 的日志可见** | 否（记为已知残余风险） |

### 2026-09-17 · 拍板「回调 value 结构化」（只读核查，零代码改动）

1. ✅ **飞书侧无任何障碍**（一手来源：官方「按钮(button)」组件文档 + 「配置卡片交互」）：

   → **碰巧没撞上，不是不会撞上**；若选 `:` 必须同时写明文约束「此标识不得用于文件名」。
