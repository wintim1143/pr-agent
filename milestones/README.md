## 为什么重排：从「纵向切层」改成「横向切片」

旧的 S0–S6 是按**技术层**纵向切的（S2 编码、S3 闸门、S4 端到端、S5 飞书……），
问题是**只有走到 S4 才能第一次看到完整链路跑起来**，前几步都是看不见的地基。

新的划分原则：**每个里程碑都是一条端到端可演示的切片**，功能从薄到厚，每一步都有可见产出。

| | 旧（S0–S6，纵向切层） | 新（M1–M6，横向切片） |
|---|---|---|
| 组织方式 | 先做地基，最后才串联 | 先跑一条最细的线，再逐段加粗 |
| 首次可见效果 | S4（第 4 步） | **M1（第 1 步）** |
| 风险暴露 | 晚期集中爆发 | 每个里程碑暴露一批 |
| 对目标仓库的写入 | S2 就要写 | **M1、M2 完全不写远端** |

> ⚠️ **M4 范围变化（2026-09-15 据实修订）**：原定义的三项 ——
> ① `git diff` 真喂 review：**已在 M2 收尾时完成**（且扩到 test/commit 三闸门，见 M2 卡 §11 归档日志）；
> ② commitlint 真校验：**经核实不适用** —— 本项目无 commitlint（无依赖 / 无配置 / 无 husky），原来让 LLM 回答的 `lintPassed` 字段已删除；
> ③ `npm test` 真跑：**唯一剩余项**。
> 因此 M4 的重定义收敛为一句话：**把凡是程序能判定的字段（测试结果、lint 结果、diff 存在性）从 LLM 手里收回，改为程序写入**。
>
> 📌 **建卡后补充的两条约束（2026-09-15，详见卡 §1 / §3）**：
> - **第 0 号前置：靶场无测试可跑**。`wintim1143/pr-agent-e2e` 是 README-only 仓库、**无 `package.json`**
>   → 「真跑 `npm test`」**当前无对象**。M4 必须先给靶场补「被测文件 + **人工预置**测试」。
>   ⚠️ 测试**必须人写** —— 若由 coding agent 自己写，就是「自己出卷自己判卷」，断言可以恒真，零信息量。
> - **必须拆字段，不能让程序覆写 `passed`**。`passed` 底下压着两个性质完全不同的问题：
>   ①「测试过了吗」（**事实**，需执行能力 → 归程序）②「需求实现了吗」（**语义**，需阅读理解 → 归 LLM）。
>   合成一个布尔值之后，事后无法分辨「判负是因为测试红」还是「模型认为需求没做」—— 排障时这条信息最贵。
>   完整判据归属表见卡 §1。⚠️ `testsPassed = null`（无测试可跑）**绝不可等价于 `true`** ——
>   这与 M2 那次让 LLM 回答 `lintPassed` 的幻觉是同构错误。

> ⚠️ **M5 范围变化（2026-09-16 据实修订）**：原定义的三项，收敛为两项 ——
> ① **GitHub App 鉴权 → 剔除**，拆为独立后置项。依据：**多仓库并不要求 GitHub App** ——
>    fine-grained PAT 的 Repository access 本就支持多选，且现已全程实测跑通 push / 开 PR / merge。
>    App 的收益（installation token 自动轮换、审计不挂个人、webhook 推送前提）属**长期运维 / 多租户**议题；
>    塞进 M5 会让一个里程碑变成两个。
> ② **幂等防重复触发 → 保留，但范围缩小**。侦察发现「防重」有两层且**上层已做、下层才是缺口**：
>    - **产物层（已做，M3）**：`githubPushAndOpenPR` 开 PR 前先查同 head 的 open PR 并复用（避免 422 重复建），
>      `githubCheckout` 也复用既有分支。→ **不改实现，只补回归断言**
>    - **入口层（缺口，M5a）**：`api.controller.ts` 自认「真实去重应在持久化游标上做，此处为最小实现」。
>      配合 `sinceTs` 默认取「一小时前」，一旦挂上定时轮询，同一条消息会被重复触发几十次
>      → 重复的 run 会重复跑 coding / review（真金白银的 LLM 调用），并让多个 run 争抢同一本地 clone
> ③ **RepoTarget 多仓库 → M5b，本里程碑主体**。
>
> 📌 **M5 最重要的一条设计约束**：`target` **只把逻辑标识（`owner`/`repo`/`baseBranch`）写进 `ContextSchema`，
> 本机 clone 路径绝不写入** —— 因为 `ContextSchema` 会被序列化进 snapshot，而 M3-5 的跨进程 resume 正是靠它恢复上下文；
> 写入本机绝对路径会让 run 快照**绑定到某台机器的文件系统**。本机路径由「仓库注册表」在运行时解析。
>
> 📌 **M5 的风险性质与 M4 不同**：M4 的风险是**假通过**（报告绿了但没验），
> M5 的风险是**静默损坏**（重复消耗 / 两个 run 争抢同一 clone 导致提交落到错误分支）。
> 后者不崩溃、不报错，因此判据必须是可数的事实（有没有第二个 run / 有没有串台），不能是「看起来正常」。
> 完整范围与 AC 见卡 §3 / §8。

> 📌 **M6 建卡说明（2026-09-16）**：M6 的定义**据实收敛**了 —— 不再写成「run 追踪 / 成本回写 / 失败告警」三条并列，
> 而是先回答一个问题：**现状到底缺什么？** 实测答案是「**缺关联，不缺日志**」：
> - `logs/dev-workflow.log` 已有 **701 行、0 非 JSON、12 种事件** —— 事件不缺；
> - 但 `runId` 字段虽在 `progress.ts:85` 已声明，**真实覆盖率 = 0/701**
>   （唯 6 条带 `runId` 的记录，值是字面量 `"rejected"` / `"resumed"` —— 见下条）；
> - 因此**多 run 事件在同一文件里交错，无法按 run 分组**，重建时间线只能绕道
>   `mastra.db` 反查 runId 再手工切分（这条手法记在 `.workbuddy/memory/ref-ops.md`）。
>
> 🔑 **根因是「位置参数误用，类型系统拦不住」**：`stageStart(stageName: string, runId?: string)` 两个形参都是
> `string`，于是 `stageStart('merge', 'rejected')` 把语义串塞进了 `runId` 槽而**编译器不报错**。
> 同时 `merge` 步的 execute 压根没解构 `runId`（而 Mastra **本来就免费提供** —— 其余六步都已解构）。
> → **M6 的修法不是加注释提醒，而是把位置参数改成对象参数，让误用无法通过编译。**
>
> 📌 **用户明确追加的要求（2026-09-16，已写入卡 §3）**：M6 **必须包含统一日志规范**；
> **有意义的输出不允许只打 `console`，至少落文件**；**最好有类似 OTEL 的 `trace_id` / `run_id`**。
> ⚠️ 但**不引入 OTEL 本体**：本项目当前没有观测后端，字段按 span 语义命名即为将来迁移留口
> —— 判据是「**可关联**」，不是「**可上报**」。
>
> 📌 **M6 → M8 是硬依赖，不是排期偏好**（⚠️ 2026-09-17 更正：原写作「M6 → M7」）：
> 飞书按钮回调的本质是「**用一个标识定位挂起的 run 并 resume**」，
> 而现状卡片用的标识是 `merge_<issueNumber>` —— 在**多仓库 + 重跑**下不唯一（见下方 M8 说明块）。
> **M6 之前这个标识不可信，M8 的按钮就是猜。**
> 📌 **M7 不依赖 M6，也不依赖 M8** —— M7 只做对话（`/ask`），不使用 `runId` 定位任何东西
> → **可以立即开工**。这是 2026-09-17 重切带来的一个直接收益：把「能聊」从「能开发」里剥出来，
> 前者不必等任何前置。
>
> 📌 **「为什么不是替代 M6」也在此一并回答**：顺序由**谁阻塞谁**决定，不由「谁更接近目标」决定 ——

> 构造双 run + **查日志确认**来验，而 `runId` 覆盖率现在是 **0/701**）。
> **六条论证见 `M8-飞书双向控制.md` §2「排序论证」。**

>
> | | **M7 飞书对话入口**（🆕 最小切片） | **M8 飞书双向控制**（原 M7 主体） |

> 而按钮回调是**事件推送**（长连接 / 回调服务器），解决「人工闸门回传」。**两者形态与作用对象都不同**：
> 轮询是**创建** run，回调是**唤醒** run。看起来同类，实际无关 → **承诺漂移得以静默发生。**
> 至今 `adapters/feishu.ts:17` 仍写「按钮回调 … 属 P1 inbound 工作」。
>
> **④ 立项前侦察出的七处缺口（决定了真实工作量，详见卡 §3）**：
> 最要紧的一条是 —— **飞书入口至今只起 `insight-workflow`（只读洞察），从来不起 `dev-workflow`（真开发）**
> （`api.controller.ts:89-94` 硬编码）；且 `dev-workflow` 要 `issueNumber`/`issueTitle`/`issueBody` 形状的入参，
> **飞书一句话喂不进去**。此外卡片按钮 value 是 `merge_<issueNumber>`（多仓库下不唯一）、
> 卡片不含 target、无长连接依赖（`package.json` 里没有飞书 SDK，现有能力是轮询）。
>
> ✅ **有利条件**：`.env` 已配 `FEISHU_APP_ID` + `FEISHU_APP_SECRET` + `FEISHU_RECEIVE_ID`（**自建应用模式**），
> 而 `card.action.trigger` 回调**只有自建应用支持** —— 飞书侧责任边界已具备，缺的只是本机接收端。
> ⚠️ 但本机在家庭网络**无公网入口** → 事件推送必须走**长连接**（§0.1 待拍板项 1），
> 或退到内网穿透 + 回调 HTTP 服务器。
>
> ⚠️ **本里程碑必须显式声明的两条风险**：① 群聊多人触发 → 并发压力上升，
> M5 已知的 `TTL(30min) > WAIT(10min)` 窗口会**被真实撞上**；
> ② **触发即执行 agent 写下的代码** → 「谁有资格触发」不是可选项，**准入控制不能被默认成「群里任何人」**。
>
> **⑤ 2026-09-17 拍板：回调标识改为结构化 `value`，不用任何分隔符**
> 用户先提议把分隔符从 `_` 换成 `:`（理由：冒号在**分词查询**上优于下划线）—— 判断成立，
> 但核查后取了更优解：`merge_<n>` 把「**哪个 run**（身份，用于定位）」与「**哪个动作**（意图，用于分支）」
> 压进同一个 token，与 M6 已修的 `stageStart('merge','rejected')` **同构**；而 `value` 在飞书侧
> **本就是 JSON 对象**（官方原文：「仅支持 key-value 形式的 JSON 结构，且 key 为 String 类型」）
> → **拼接是自造的，不是接口要求**。结构化让「分词 / 字符集 / 唯一性」三个问题同时消失。
> 形态：dev `{ kind:'dev', action:'merge'|'reject', runId, repoKey }` /
> insight `{ kind:'insight', action:'confirm'|'rerun', runId }`。
> 详见 `M8-飞书双向控制.md` §7 M8-3（含字段必要性表）与 §11 记录 2026-09-17。
> ⚠️ 同批更正一处**假约束**：`docs/archive/11-IM驱动的多Agent自动开发工作流设计.md:125` 的
> 「`callback_id` ≤128、仅字母数字下划线短横线」**在飞书官方文档里查无支撑**，勿引用。
> 完整范围 / 七项缺口 / 13 条 AC 见卡 §3 / §8。

## 全局原则

1. **每个里程碑必须有一条可演示的链路**，不接受「只加地基、看不到效果」。
2. **不写远端仓库的先做**。M1/M2 全部只读或只写本地分支，避免污染历史、也绕开了 D4（目标仓库选型）这个未决项。
3. **能用 Mastra 官方抽象就不裸写**。同样一个功能，优先落到 Mastra 的模块上（Integration / Tool / Workflow / Storage / Agent），
   而不是自己 new 一个 fetch 封装——这样踩过的坑和学到的东西是可迁移的。
4. **每张卡按 🟦定义期 / 🟨实施期 分层填写**（模板第 1–4 节定义期必填，第 5–10 节实施期渐进补全）。源码级证据（行号 / 实测命令 / 接口路径）只进「实施日志·已核实事实」，不进正文。
5. **完成后立刻归档**：改了什么、重点模块、踩坑，写进实施日志，不等到里程碑收尾。
6. **每个里程碑配一张数据流向图（流程图 / 时序图）**，展示「触发 → 编排 → 集成 → 外部系统」及 suspend/resume 断点。推荐用 Mermaid 写在独立文件 `M<n>-<名称>-flow.md`，卡片只放链接。
7. **记录不强制单文件**：里程碑卡可只做索引，链路图 / 流程图 / 实施日志 / 复盘等拆到同目录的独立文件（或子目录），便于单篇查看与演进。
8. **失败路径显式声明**：每个里程碑在卡的「异常与兜底」节列出「已知异常 → 判定条件 → 降级行为 → 是否阻断 AC」，判定条件必须可执行（返回码 / 超时秒数 / 配置缺失），不许写无法判定的表述。M1 的教训：外部依赖（LLM 中继）挂起曾冻结整条 suspend/resume 闭环，靠「超时+重试+降级」才解掉。
9. 🆕 **「不做项」不许悬空（2026-09-16 据原 M7 立卡的教训补入）**：卡里写「本里程碑不做，**推迟到 M<n>**」——
   这是在开一笔**无主债务**：下个里程碑不主动承接，它就静默变成孤儿。
   **双向都要扫**：① 本卡开出的承诺，收口时逐条定性为「承接 / 移交某卡 / 声明不再做」；
   ② 前几张卡承诺给本卡的，建卡前 `grep -rn "推迟到 M\|留给后续" milestones/*.md` 捞出来核对。
   判定口诀：**「看起来有人负责」≠「有人负责」** —— 要能指出是哪张卡的哪个任务。
   反面教材：飞书卡片按钮回调被 M2/M3/M4 **四处**写成「推迟到 M5」，M5 卡却全文没有这一项，
   因为它们**形态不同**（M5 做的是轮询创建 run，回调是事件推送唤醒 run）→ 顺势漂了三个里程碑，最终由 M8 收口
   （原 M7；2026-09-17 重切后按钮回调归 M8 —— 二次分拆时这条债又被重新定性了一遍，见 M8 卡 §0.2）。
