> 本手册回答一个问题：**「跑通了」是怎么判定的？**

> 与里程碑卡的 AC 对应关系见每节表格。最后更新：2026-09-04。

## 2. M1 验证：三种形态，同一套 AC

M1 = 飞书一句话 → GitHub 只读 → LLM 洞察 → 卡片回推 → 人工确认。

### 形态 A：脚本直验（最常用，不依赖服务）

```bash
cd /d/code/pr-agent
npm run build            # 先确保 dist/ 最新
node scripts/verify-insight-loop.js
```

- 进程内走完整闭环：`createRun → start(suspend 在 confirm) → resume({approved:true})`。
- 输出会打印每步判定；完整留档在 `logs/m1-verify.log`。

### 形态 B：人工验收模式（验证 suspend/resume 交互）

```bash
M1_MANUAL_CONFIRM=1 node scripts/verify-insight-loop.js
```

- 跑到 confirm 步会**挂起等你终端输入**，输 `y` 才 resume —— 用于演示「人工闸门」语义。

### 形态 C：HTTP 服务（等价于真实 IM 入口）

```bash
npm run build && npm start        # 起在 http://localhost:8001
```

**① 确认 workflow 已注册**
```bash
curl -s http://localhost:8001/api/workflows | grep -o '"id":"[^"]*"'
# 应看到 insight-workflow
```

**② 触发一条洞察**（等价飞书发一句话）
```bash
curl -s -X POST http://localhost:8001/api/insights \
  -H "Content-Type: application/json" \
  -d '{"query":"最近项目有哪些进展和潜在风险?"}'
# 期望: {"success":true,"runId":"cm7x...","status":"suspended"}
# status=suspended 即 collect→summarize→notify→confirm 挂起全走完;耗时取决于 LLM 中继,可能 30s+
```

**③ 人工确认**（等价点卡片按钮；这是 Mastra 内建 resume 端点）
```bash
curl -s -X POST "http://localhost:8001/api/workflows/insight-workflow/resume?runId=<上一步的runId>" \
  -H "Content-Type: application/json" \
  -d '{"resumeData":{"approved":true}}'
# 期望: steps.confirm.output.feedback = "confirmed", 且 steps.collect.output.issues 非空(=上下文恢复)
```

**④（可选）查 run 明细**
```bash
curl -s "http://localhost:8001/api/workflows/insight-workflow/runs/<runId>"
curl -s http://localhost:8001/api/workflows/insight-workflow/runs
```

### AC 判据速查（M1）

| AC | 判据 | 在哪看 |
|---|---|---|
| AC-1 | runId 生成、非空 | 形态 A 输出 / 形态 C ②响应 |
| AC-2 | GitHub 真实数据（issue/commit 非空） | 形态 A `AC-2 GitHub 数据` 行 |
| AC-3 | 真实洞察内容（highlights/risks/suggestions 各 5 条，`llmUnavailable=false`） | 形态 A / 飞书卡片内容 |
| AC-3b | 飞书卡片真发到群 | **人工去飞书群看卡片**（5 进展/5 风险/5 建议） |
| AC-4 | run 停在 confirm 步（status=suspended） | 形态 A `✓ AC-4` / 形态 C ② |
| AC-5 | resume 后 feedback=confirmed、上下文不丢（issues 数仍在） | 形态 A `AC-5 人工反馈` / 形态 C ③ |
| AC-6 | 零写入：git status 无 db/log 运行产物 | `git status --short | grep -iE "mastra.db|\.log$"` 应为空 |
| AC-7 | 不配置不阻塞：清空 GITHUB_TOKEN / FEISHU_* 仍走通 | 空配置重跑形态 A |

> 飞书卡片上点按钮报「目标回调服务当前未在线」= **预期行为**：按钮回调（inbound）设计上推迟到 M5，M1 验收不依赖它。AC-3b 的「推送卡片」已证明推通；「点按钮回传」是 inbound，不在 M1 范围。

## 3. M2 前置探针：四个脚本的用途与判据

探针脚本全部位于 `scripts/`，命名 `_*.js` 表示诊断用，**不进入产品代码**。

| 脚本 | 打什么 | 判据（通过 =） |
|---|---|---|
| `_coding-probe.js` | 临时目录靶场起真实编码 agent（Claude Code CLI），读 hello.txt → 写 hello.upper.txt | `hello.upper.txt 是否存在 = true`，内容为原文大写 |
| `_messages-probe.js` | `POST /v1/messages`：步骤1 无 tools 纯文本 / 步骤2 带 tools | 步骤1 HTTP 200；步骤2 `stop_reason: tool_use` 且返回 Read 调用 |
| `_relay-protocol-probe.js` | 同一中转站四种协议横评（/chat/completions、/responses、/v1/messages） | 各端点 HTTP 200（非 502）即端点存在 |
| `_ccswitch-proxy-probe.js` | 打 cc-switch 本地代理 `127.0.0.1:15721` 的 /v1/messages | HTTP 200 + tool_use |

**为什么要四个分开**：把「CLI 起不来」「协议不支持」「端点不存在」「上游中断」四类故障拆开定位，避免一次探针失败不知道怪谁。

### 跑法

```bash
cd /d/code/pr-agent && npm run build
node scripts/_coding-probe.js          # 端到端,内部守卫 240s
node scripts/_messages-probe.js        # 协议级
node scripts/_relay-protocol-probe.js  # 协议横评
node scripts/_ccswitch-proxy-probe.js  # 本地代理
```

> ⚠️ `_coding-probe.js` 的靶场在 OS 临时目录（`%TEMP%\pr-agent-coding-probe-*`），**不碰 pr-agent 工作树**。跑完靶场路径会打印，可自行清理。

## 3.5 M2 闭环验证：`verify-local-write.js`

前置探针只证明「编码后端能用」；这一节验证的是**整条编排**在隔离沙箱里跑通本地写入闭环。

```bash
cd /d/code/pr-agent && npm run build
node scripts/verify-local-write.js              # 正常编码任务(会真改文件 + 真 commit)
node scripts/verify-local-write.js --reset      # 重跑:先重置沙箱(main + 删 feat/*)
node scripts/verify-local-write.js --redline    # 红线模式:要求 agent 改 agent.md,验证拦得住
node scripts/verify-local-write.js --turns 1    # 覆盖 CODING_MAX_TURNS,观察失控上限行为
```

| 项 | 值 |
|---|---|
| 靶场 | `D:\code\pr-agent-sandbox`（本地仓库，**无 remote**，物理上不可能 push） |
| 安全机制 | 脚本**硬设** `CODING_REPO_ROOT` 指向沙箱（不依赖外部环境）；运行前检查沙箱干净；运行后比对 pr-agent 工作树快照 |
| 入参 | `{ issueNumber, issueTitle, issueBody, stopAfterCommit: true }` —— 最后一项让 workflow 停在 commit，不 push / 不 notify / 不 suspend |
| 证据 | `logs/m2-verify.log` |
| 退出码 | `0` 全通过 / `2` 有 AC 未过 / `1` 前置检查或 workflow 异常 |

**判定项**：AC-1 分支名 / AC-2 改动文件 / AC-3 codingResult 非占位 / AC-7 三闸门结构化 / AC-8 commit 落盘 / AC-9 零远端 / AC-10 pr-agent 未被触碰。AC-4/5/6（红线）主证据是 `test/mastra/guard*.test.ts` 的 60 个单测，`--redline` 补真实 CLI 集成下的最终安全属性。

> ⚠️ AC-10 判的是「运行前后 **不变**」而非「干净」——开发期间 pr-agent 本身常有未提交改动，要求它干净会恒定失败。

## 4. 当前已知阻塞：reg.exe（2026-09-04 状态）

### 现象
Claude Code CLI（本机 v2.1.258）在 Windows 启动时会 spawn `C:\Windows\System32\reg.exe`，在 **WorkBuddy 沙箱**里被 Program Blacklist 拦截，SDK 驱动的 generate() 卡死到超时（240s 零输出）。

### 定性（一手来源）
- **官方已知 regression**（GitHub anthropics/claude-code issue #33100）：2.1.49 之后启动**无条件** spawn reg.exe，被拦则 EPERM 崩溃；2.1.49 是最后不碰它的版本。
- 用途 = **Claude in Chrome 集成的 native-messaging host 注册**（issue #14507 源码证据：`reg add ... REG_SZ`）。
- 官方未修；settings.json 196 个键无 chrome 相关、无透传任意 CLI flag 机制；SDK `Options` 无 `--no-chrome` 字段。
- CLI 有 `--no-chrome` flag（`claude --help` 可见）但代码层无法注入（SDK 不透传）。

### 重要事实：拦截是 WorkBuddy 沙箱特有
reg.exe 在 WorkBuddy 沙箱的 Program Blacklist 里 —— **普通终端/服务器没有这个黑名单**。因此 M2 编码闭环可以在沙箱外跑通。

### 两条出路

| 路径 | 做法 | 适用 |
|---|---|---|
| A. 沙箱外跑 | 在用户自己的终端/服务器跑 `node scripts/_coding-probe.js` | 亲自驱动开发或最终部署到服务器 |
| B. 沙箱内放行 | Security Center → Command Security → Program Blacklist 移除 reg.exe | 需要自动化（由 agent 驱动 workflow coding 步） |

### 判据
- 探针输出 `hello.upper.txt 是否存在 = true` → 编码后端可用，M2 可开工。
- 若在沙箱外仍超时 → reg.exe 之外另有问题，需继续排查。

## 6. 为什么这些验证值得信

- 每条 AC 判据**可执行、可复跑**，证据落 `logs/`，不是「看起来对了」。
- 探针与产品代码解耦：先证明「后端能驱动 tool_use」，再让 workflow 依赖它 —— M2 建卡时不需要在卡上写假设。
- M1 曾因 LLM 中继不稳定降级（AC-3 空洞察），靠「超时+重试+降级」撑过；9-04 中继恢复健康后全量复验拿到真实 5/5/5 洞察，才关闭闸门 —— **验证必须在中继健康窗口做才有意义**。
